SB-106App crashed on launch - FirestoreService resolved before it was registeredCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Startup / DI
Status
Fixed in 1.0.0+2
Root cause / fix
_initFirebaseSafely() called sl<FirestoreService>() while configureDependencies() had not registered it yet. The throw propagated out of the method, so every registration after that line was skipped and main() then crashed on sl<ThemeCubit>(). The static analyser cannot see an ordering bug inside a service locator; only launching the app exposed it.
SB-107App crashed on start-up - AuthRepositoryImpl resolved by its concrete typeCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Startup / DI
Status
Fixed in 1.0.0+2
Root cause / fix
main() called sl<AuthRepositoryImpl>() for the demo-account seed, but the repository is deliberately registered against the AuthRepository interface. Resolving the concrete type is exactly what interface-only registration is meant to prevent. The seed moved into the composition root (injection.dart), which is where bootstrap concerns belong.
SB-108Login always failed with a valid account whenever Firebase was reachableCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Authentication
Status
Fixed in 1.0.0+2
Root cause / fix
The QA account was seeded only in the on-device fallback store. AuthRepositoryImpl tries Firebase first and correctly refuses to mask a real credential rejection, so the sign-in was rejected with 'Incorrect email or password.' The bootstrap now registers the account in Firebase Auth as well, and writes the display name when the account is first created.

SB-110Login screen was unreachable - the app was permanently signed inCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Authentication
Status
Fixed in 1.0.0+2
Root cause / fix
Found by the Appium round, not by the manual one: every automated run failed on 'the Login form never appeared'. The QA-account seed called createUserWithEmailAndPassword, which authenticates the user as a side effect, and never signed out again. Firebase persists that session, so restoreSession() always returned a user and the splash always routed to Home - including straight after 'adb shell pm clear'. The seed now signs out in a finally block. A related throttling risk was removed at the same time: re-signing-in on every cold start is now unnecessary, since the display name persists server-side.

Status
Fixed in 1.0.0+2
Root cause / fix
The screen pre-filled the demo credentials 'so the Appium suite can log in'. That is a security smell on a real sign-in screen, and it also made TC-LOGIN-003 untestable: WebElement.clear() does not clear a Flutter TextFormField, so the 'empty form' test actually submitted the pre-filled credentials and signed in. SB-113Automation: every test reported 'Login form never appeared' - a null driverCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Automation harness
Status
Fixed in 1.0.0+2
Root cause / fix
LoginPage and HomePage extended BaseTest but were constructed with only a WebDriverWait, so they read an inherited `driver` field from their own uninitialised instance. The resulting NullPointerException was swallowed by the wait helper and re-thrown as a UI timeout, which sent the investigation after the app instead of the harness. Fixed by converting both page objects to composition (the live AndroidDriver is injected) and by making Waits.until rethrow anything that is not a genuine TimeoutException. The added page-source capture is what proved it: no findElement had ever been issued.
SB-114Cloud Firestore denied every read and write - the project had no rules fileCritical
Case
TC_HOME_009
Severity
Critical · priority High
Component
Backend / Firestore
Status
Fixed in 1.0.0+3
Root cause / fix
The Firebase project was created without a firestore.rules file, leaving the database in its default locked state. Every call returned PERMISSION_DENIED: 'Missing or insufficient permissions', which silently broke the Profile screen, the favourites list and the order history while Firebase Auth kept working - so the app looked mostly fine and only the Firestore-backed screens failed. The repository layer could not mask it either, because FirestoreService.isAvailable only reports whether the SDK initialised, never whether the rules permit access. Owner-scoped rules were written and deployed (firestore.rules).
SB-115The app signed the user out of their own session on every launchCritical
Case
TC_LOGIN_001
Severity
Critical · priority High
Component
Authentication
Status
Fixed in 1.0.0+3
Root cause / fix
The QA-account seed called createUserWithEmailAndPassword, which signs the new user in as a side effect, and then signed out in a `finally` block. Because the seed runs on EVERY launch, a real user who had signed in was signed straight back out: the splash restored the session and the seed destroyed it a moment later, so the next cold start had nothing to restore. Fixed by tracking whether the seed actually authenticated anyone, and signing out only in that case.
SB-116A 'zombie session' showed an authenticated UI while the backend had no sessionCritical
Case
TC_HOME_009
Severity
Critical · priority High
Component
Authentication
Status
Fixed in 1.0.0+3
Root cause / fix
restoreSession() fell back to the on-device session store when Firebase had no current user. Combined with SB-115 that produced a screen that looked fully signed in while every Firestore request carried no auth token - so favourites and orders rendered 'We couldn't reach StreetBite' behind a Retry that could never succeed. When Firebase is usable it is now the only authority on whether anyone is signed in; the local store is consulted only when Firebase is unavailable.
SB-117The Profile tab was permanently unreachable when biometrics could not succeedHigh
Case
TC_PROFILE_001
Severity
High · priority Medium
Component
Authentication / UX
Status
Fixed in 1.0.0+3
Root cause / fix
Both entry points to the profile passed bypassAllowed: false. On a device whose biometrics can never succeed - no hardware, nothing enrolled, sensor locked out - tapping the avatar flashed a four-second SnackBar reading 'Biometric check failed. Try again.' and left the user staring at the gate forever. Retrying could not help and there was no way forward. Viewing a profile is not a privileged action, so the gate now always offers 'Continue without biometrics'.
SB-118The Profile screen re-queried Firestore on every rebuildMedium
Case
TC_PROFILE_003
Severity
Medium · priority Medium
Component
Performance
Status
Fixed in 1.0.0+3
Root cause / fix
_ProfileView called FavouritesCubit.load() and OrdersCubit.load() directly inside build(). Every rebuild - including the one triggered by those very calls emitting their result - fired both queries again, so the screen hammered Firestore continuously and any transient failure left a stale error view behind. Loading is now done once per uid from initState via addPostFrameCallback.
SB-119Google Maps API key is rejected - the map renders blank and could freeze the appHigh
Case
TC_MAP_001
Severity
High · priority Medium
Component
Maps / Credentials
Status
Partially fixed in 1.0.0+3
Root cause / fix
The Maps SDK logs 'Error requesting API token. StatusCode=INVALID_ARGUMENT' and 'Authorization failure' for the configured key, so no tiles are drawn and the screen was solid black. Worse, Google's SDK retries token acquisition on the UI thread, and on one attempt Android declared an ANR - 'StreetBite isn't responding' - and killed the app. The app side is mitigated: the map now has a startup deadline and falls back to a readable error view with Retry instead of blocking. THE KEY ITSELF STILL NEEDS FIXING in Google Cloud Console (enable Maps SDK for Android, or supply a valid key in android/key.properties); that part is outside the repository and remains OPEN.
