StreetBite code documentation · §07 Data & resilience

StreetBite code documentation · Part I · Section 07 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 07 من 18 · الفهرس الكامل

07 · Data & resilience07 · البيانات والصمود

StreetBite talks to five different backends at once: a public REST API, a key-value store, Firebase Authentication, Cloud Firestore, and a compiled-in list of five vendors. Only one of them is guaranteed to be reachable on any given launch — so the design rule is not "handle the error" but "always show something". Every read has a defined degraded answer, and every write has a defined outcome when the backend is gone.

That rule is why the app is demonstrable on an emulator with no Google Play Services, offline in a train, and against a Firebase project whose rules were misconfigured.

يتواصل StreetBite مع خمسة خلفيات مختلفة في وقت واحد: واجهة REST عامة، ومخزن مفاتيح وقيم، وFirebase Authentication، وCloud Firestore، وقائمة مضمّنة في الكود لخمسة باعة. ولا يُضمَن منها إلا واحد في أي إقلاع، لذا لم تكن قاعدة التصميم «عالِج الخطأ» بل «اعرض شيئًا دائمًا». لكل قراءة جواب معرَّف عند التدهور، ولكل كتابة نتيجة معرَّفلة عندما يغيب الخادم.

هذه القاعدة هي سبب قابلية التطبيق للعرض على محاكي بلا خدمات Google Play، وفي وضع عدم الاتصال، وحتى مع مشروع Firebase ضُبطت قواعدُه خطأً.

The menu: a Factory that chooses a source, not a classالقائمة: مصنع يختار المصدر لا الصنف

MealRepositoryImpl owns an enum — remote, local, remoteThenLocal — and one method, selectDataSource(), that maps an intent onto a strategy. The decision has exactly one home instead of a switch repeated at every call site, and it can be unit-tested on its own. Adding a third backend is one enum value and one branch there; no other file changes.

defaultSource is remoteThenLocal: try TheMealDB, write the result into the cache, and on NetworkException read the cache instead of showing an error screen. Both getMeals() and getHotOffers() use it.

The cache stores the whole list under one key. That is a deliberate trade-off, stated in the file's own comment: TheMealDB returns around fifty small records, so one read is cheaper than fifty, and the payload stays trivially inspectable during QA. Hot Offers get their own key (streetbite_cache_hot_offers) so a failure to cache the offers can never invalidate a good menu cache.

يمتلك MealRepositoryImpl تعدادًا — remote وlocal وremoteThenLocal — ودالة واحدة هي selectDataSource() تربط نيةً بـستراتيجية. فالقرار له موطن واحد بدل switch يتكرر عند كل استدعاء، ويمكن اختبارُه بمفرده باختبار وحدة مستقل. وإضافة خلفية ثالثة هي قيمة للتعداد وفرع هناك فقط، دون تغيير أي ملف آخر.

defaultSource هو remoteThenLocal: جرّب TheMealDB، ثم اكتب النتيجة في المخزون، وعند NetworkException اقرأ المخزون بدل عرض شاشة خطأ. ويستخدمه كلٌّ من getMeals() وgetHotOffers().

يخزّن المخزون القائمة كاملة تحت مفتاح واحد. وهذا مقايضة مقصودة يشرحها تعليق الملف نفسه: يرجع TheMealDB نحو خمسين سجلًّا صغيرًا، فتصير قراءة واحدة أقل كلفة من خمسين، وتبقى الحمولة سهلة الفحص أثناء ضبط الجودة. وتأخذ العروض الساخنة مفتاحها الخاص (streetbite_cache_hot_offers) حتى لا يستطيع إخفاق تخزين العروض إفساد مخزون قائمة سليم.

Auth: the on-device fallback, and the line it must not crossالمصادقة: الرجوع المحلي والحدّ الذي لا يُتجاوز

Authentication is the most interesting degradation because it is the one place where being helpful and being unsafe are one line apart. AuthRepositoryImpl keeps a flag, _firebaseUsable, and consults _isConnectivityFailure() before switching to AuthLocalDataSource. Only authErrorNetwork and authErrorUnknown count as connectivity.

A credential rejection is not connectivity. Falling back for a wrong password would let that password succeed offline — a false pass, and one that would have made the whole Appium suite meaningless.

The local store keeps a list of JSON objects under streetbite_local_users and the session under streetbite_local_session. Passwords are never clear text: they pass through a salt-and-hash function built on the FNV-1a constants (offset basis 0x811c9dc5, prime 0x01000193, masked to 32 bits). Local accounts get an id like local-1725834000123456 — microseconds since epoch, so it cannot collide with a Firebase uid — and the seeded QA account gets the fixed id streetbite-demo-uid.

The same store also holds the biometric opt-in under streetbite_biometric_sign_in. It is device-local on purpose: the same account on a tablet with no enrolled fingerprint must not inherit an opt-in it can never satisfy.

المصادقة هي أكثر حالات التدهور إثارة لأنها الموضع الذي يفصل فيه سطر واحد بين المفيد وغير الآمن. يحتفظ AuthRepositoryImpl بعلم هو _firebaseUsable، ويستشير _isConnectivityFailure() قبل الانتقال إلى AuthLocalDataSource. ووحدهما authErrorNetwork وauthErrorUnknown يُعدّان انقطاع اتصال.

أما رفض بيانات الاعتماد فليس انقطاع اتصال. ولو رجعنا عند كلمة مرور خاطئة لنجحت تلك الكلمة أثناء عدم الاتصال — وهي نتيجة خاطئة كانت ستُفقد حزمة Appium معناها كله.

يحفظ المخزن المحلي قائمة كائنات JSON تحت streetbite_local_users والجلسة تحت streetbite_local_session. ولا تكون كلمات المرور نصًا صريحًا أبدًا: تمرّ بدالة تمليح وتجزئة مبنية على ثابتي FNV-1a (الأساس 0x811c9dc5 والعدد الأولي 0x01000193، مع قناع إلى 32 بت). وتأخذ الحسابات المحلية معرّفًا مثل local-1725834000123456 — ميكروثانية منذ الحقبة، فلا يتصادم مع uid في Firebase — بينما يحصل حساب ضبط الجودة المزروع على المعرّف الثابت streetbite-demo-uid.

يحمل المخزن نفسه موافقة البصمة تحت streetbite_biometric_sign_in. وهي محلية على الجهاز عن قصد: فالحساب نفسه على لوحي بلا بصمة مسجَّلة لا ينبغي أن يرث موافقة لا يستطيع الوفاء بها أبدًا.

Firestore: one gateway, one place where the schema is namedFirestore: بوابة واحدة، وموضع واحد تُسمَّى فيه المجموعات

FirestoreService is the app's only eager-shared object: a private constructor plus a static final _instance and a factory that returns it, so the class cannot be instantiated from outside its own library. GetIt registers it as a lazySingleton, created on first use and shared for the whole lifecycle.

Two things make it more than a pass-through:

  • configure(null) is a supported state. When Firebase.initializeApp() fails, the service stays in "local mode": isAvailable is false and every repository answers from its own local logic. Touching the firestore getter anyway throws FirestoreNotAvailableException — loud in a test, invisible to a user.
  • Collection names are declared once — in AppConstants, not in these accessors. usersCollection(), ordersCollection(uid) and favouritesCollection(uid) do spell out users/{uid}, orders/{uid}/items and users/{uid}/favourites at firestore_service.dart:62-70 — and nothing calls them. The three repository implementations build the same paths from AppConstants.usersCollection, AppConstants.ordersCollection and AppConstants.userFavouritesSubCollection and hand the finished strings to the generic read/write helpers. The schema is still centralised, but the real source of truth is the constants file; these accessors are dead weight kept beside it, and AppConstants.favouritesCollection has no reader either.

Writes use SetOptions(merge: true) rather than set, so a profile update that changes only the display name cannot delete the stored photo URL.

FirestoreService هو الكائن الوحيد المشترك مشاركة مبكّرة في التطبيق: مُنشئ خاص مع static final _instance وfactory يعيده، فلا يمكن إنشاء الصنف من خارج مكتبة نفسه. ويسجّله GetIt كـlazySingleton، فيُنشأ عند أول استعمال ويشترك فيه طوال العمر التشغيلي.

وأمران يجعلانها أكثر من مجرد غلاف رقيق للمكتبة:

  • configure(null) حالة مدعومة. عند فشل Firebase.initializeApp() تبقى الخدمة في «الوضع المحلي»: isAvailable خاطئة، ويجيب كل مستودع من منطقه المحلي. ولمس firestore رغم ذلك يرمي FirestoreNotAvailableException — صاخبًا في اختبار، خفيًّا عن مستخدم.
  • أسماء المجموعات معلنة مرة واحدة — في AppConstants لا في هذه الأدوات. فإن usersCollection() وordersCollection(uid) وfavouritesCollection(uid) تكتب فعلًا users/{uid} وorders/{uid}/items وusers/{uid}/favourites في firestore_service.dart:62-70 — ولا يستدعيها أحد. فتنفيذات المستودعات الثلاثة تبني المسارات نفسها من AppConstants.usersCollection وAppConstants.ordersCollection وAppConstants.userFavouritesSubCollection وتمنح السلاسل الجاهزة لدوال القراءة والكتابة العامة. فالمخطط ما زال مركزيًا، لكن مصدر الحقيقة هو ملف الثوابت؛ وهذه الأدوات وزن ميت بجانبه، وAppConstants.favouritesCollection بلا قارئ أيضًا.

وتستخدم الكتابات SetOptions(merge: true) لا set المجردة، فلا يمكن لتحديث ملف شخصي يغيّر الاسم المعروض وحده أن يمحو رابط الصورة المخزَّن.

Offline writes: the honest limitationالكتابة بلا اتصال: القيد مذكور بصدقه

Read this before calling it a queue · اقرأ هذا قبل تسميته طابورًا

When Firestore is unavailable, OrderRepositoryImpl.placeOrder() returns Right(order.id) without writing anything, and getOrderHistory() returns Right([]). The intent is explicit in the code comment: the checkout flow completes and the user is not blocked by a backend outage. The consequence is equally real — there is no outbox. An order placed offline is accepted, confirmed on screen with an id, and then never reaches the server. Reading history offline shows an empty list, not stale data, so the Orders tab renders its empty state rather than an error. Fixing this properly means a pending-writes table plus a replay on reconnect; that is out of scope for V1 and is recorded here rather than hidden.

عند تعذّر Firestore تُعيد OrderRepositoryImpl.placeOrder() قيمة Right(order.id) دون كتابة شيء، وتُعيد getOrderHistory() قيمة Right([]). والنية مصرَّح بها في تعليق الكود: يكتمل مسار إتمام الطلب ولا يتعطل المستخدم بانقطاع الخادم. والنتيجة حقيقية بالقدر نفسه — فلا يوجد صندوق صادر. فالطلب المُنشأ أثناء عدم الاتصال يُقبل، ويُؤكَّد على الشاشة بمعرّف، ثم لا يصل إلى الخادم أبدًا. والقراءة بلا اتصال تُظهر قائمة فارغة لا بيانات قديمة، فيعرض تبويب الطلبات حالته الفارغة لا خطأه. والإصلاح الصحيح يحتاج جدول كتابات معلَّقة مع إعادة إرسال عند عودة الاتصال؛ وهو خارج نطاق النسخة الأولى، وقد ذُكر هنا بدل إخفائه.

Money is derived, not fetchedالمال مشتق لا مجلوب

TheMealDB is a recipe API and has no prices. MealModel.fromJson therefore derives one deterministically from the meal id: (699 + (seed % 1800)) / 100, which puts every dish between $6.99 and $24.99. The same meal always costs the same thing on every launch and on every device, so cart totals are reproducible and testable — which is why a unit test can assert an exact total instead of a range. AppConstants.baseMealPrice = 8.99 is the separate fallback used when a meal has no usable id at all.

TheMealDB واجهة وصفات ولا أسعار لديها. لذا يشتقّ MealModel.fromJson سعرًا حتميًّا من معرّف الطبق: (699 + (seed % 1800)) / 100، وهو يضع كل طبق بين ‎$6.99 و$24.99. فيبقى سعر الطبق نفسه في كل إقلاع وعلى كل جهاز، فتصير مجاميع السلة قابلة للتكرار والاختبار — ولهذا يستطيع اختبار الوحدة أن يجزم بمجموع دقيق لا بمدى. أما AppConstants.baseMealPrice = 8.99 فهو الرجوع المنفصل عند انعدام معرّف صالح للطبق.

Network layerطبقة الشبكة

DioClient is a thin wrapper registered once, because a second instance would open a second connection pool. All transport concerns live inside it — three timeouts of 20 seconds, JSON response type, and one interceptor that turns every DioException into a NetworkException with a human-readable reason: timeout, offline, badCertificate, cancelled, or status_<code> for a bad response, which keeps the status code on the exception for diagnostics. A malformed URL can still slip past the interceptor, so getJson() has a final catch that unwraps error.error if it is already a NetworkException and wraps it if it is not.

One honest gap: _fetch() catches SerializationException only in the remoteThenLocal branch. The remote branch would let one escape — harmless today, since no call site uses remote, but it is the place to look first if a third source is ever added.

DioClient غلاف رفيع مسجَّل مرة واحدة، لأن إنشاء مثال ثانٍ يفتح مجمِّع اتصالات ثانٍ. وكل شؤون النقل داخله: ثلاث مهل كل واحدة عشرون ثانية، ونوع استجابة JSON، ومعترِض واحد يحوّل كل DioException إلى NetworkException بسبب مفهوم للبشر: timeout أو offline أو badCertificate أو cancelled، أو status_<code> لاستجابة سيئة، مع حفظ رمز الحالة على الاستثناء للتشخيص. ورابط مشوَّه قد يفلت من المعترِض، فوضعت getJson() التقاطًا أخيرًا يفكّ error.error إن كان NetworkException أصلًا ويلفّه إن لم يكن.

وفجوة واحدة نقولها بصدق: يلتقط _fetch() الـSerializationException في فرع remoteThenLocal وحده، أما فرع remote فيدعه يفلت — وهو غير ضار اليوم لأن لا أحد يستعمل remote، لكنه أول موضع يُنظر فيه إن أُضيف مصدر ثالث.
