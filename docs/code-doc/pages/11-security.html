StreetBite code documentation · §11 Security & privacy

11 · Security & privacy11 · الأمان والخصوصية

Read the frame first · اقرأ الإطار أولًا

StreetBite is a teaching capstone, not a hardened product. This section states what is actually defended, what is deliberately loosened so the app can be demonstrated offline, and what is only a demo. Anything that would need to change before a real release is named as such instead of being described as good.

StreetBite مشروع تخرّج تعليمي لا منتج مُحصَّن. تذكُر هذا القسم ما هو مدفوع فعلًا، وما هو مُرخًى عن قصد حتى يُعرض التطبيق دون اتصال، وما هو تجريبي فقط. وكل شيء يجب تغييره قبل إصدار حقيقي مذكور بهذا الاسم، لا بوصفه حسنًا.

Biometrics: six outcomes, classified onceالبصمة: ست نتائج، تُصنَّف مرة واحدة

No file in the app imports local_auth except BiometricService. It asks three questions before prompting — isDeviceSupported(), canCheckBiometrics, and getAvailableBiometrics().isNotEmpty — and the third one is the reason the flow works. canCheckBiometrics answers "is this device capable?", which stays true on a handset with a sensor nobody ever enrolled a finger on; offering such a user a prompt guarantees a failure. The enrolled check turns that into a precise message instead.

local_auth 3.x replaced PlatformException with LocalAuthException, which carries a LocalAuthExceptionCode. Matching on that enum is what makes the mapping exact — the previous implementation substring-matched error.toString(), so a renamed platform code silently degraded to a generic "try again". The switch keeps a default arm on purpose: the plugin documents that new codes can appear without a major version bump.

لا ملف في التطبيق يستورد local_auth غير BiometricService. ويسأل ثلاثة أسئلة قبل الطلب: isDeviceSupported() وcanCheckBiometrics و getAvailableBiometrics().isNotEmpty. والثالث هو سبب نجاح المسار: فـ canCheckBiometrics تجيب «هل هذا الجهاز قادر?» — وتبقى صحيحة على هاتف له حساس لم يسجل عليه أحد بصمة قطّ. وعرض طلب على مثل هذا المستخدم يضمن الفشل، فتحويل ذلك إلى رسالة دقيقة هو فعل الفحص الثالث.

استبدلت local_auth 3.x الـPlatformException بـLocalAuthException الذي يحمل LocalAuthExceptionCode. والمطابقة على هذا التعداد هي ما يجعل الربط دقيقًا؛ كان التطبيق السابق يطابق مقاطع نصية من error.toString()، فيصير رمز معدَّل في صمت إلى «حاول مرة أخرى». ويُبقي التبديل فرع default عن قصد، لأن الإضافة توثّق أن رموزًا جديدة قد تظهر دون ترقية كبرى.

A real gap this audit found · فجوة وجدها هذا الفحص

BiometricResult.lockedOut() carries the key biometricLockedOut, and that key is present in both ARB files with the right sentence ("Too many failed attempts. Biometric unlock is locked for now."). But L10nX.trKey has arms for only four biometric keys — failed, notEnrolled, notSupported, cancelled — so a lockout falls through to the default and the user reads "Something went wrong". The behaviour is safe, the message is merely imprecise; wiring the missing arm is a one-line change.

يحمل BiometricResult.lockedOut() المفتاح biometricLockedOut، وهذا المفتاح موجود فعلًا في ملفَي ARB بجملة صحيحة («كثير من المحاولات الفاشلة…»). لكن L10nX.trKey فيه أربعة فروع للبصمة فقط: failed وnotEnrolled وnotSupported وcancelled، فيسقط القفل إلى الفرع الافتراضي ويقرأ المستخدم «حدث خطأ ما». والسلوك آمن، والرسالة غير دقيقة فحسب؛ وربط الفرع الناقص تغيير سطر واحد.

The two gates, and what a failed scan does not doبوّابتان، وما لا تفعله بصمة فاشلة

openBiometricGate() is one function used by both gates — the avatar button on Home that guards the Profile screen, and the sign-in screen on a cold start. Its policy: success calls onUnlocked; anything else shows a dialog explaining the reason, with "Continue without biometrics" when bypassAllowed is true. The reason string is read from context before the await, and the result is guarded by context.mounted, because the OS prompt can outlast the widget.

The decision that matters most is what a failed scan does to the session. AuthCubit.fallBackToPassword() deliberately does not call signOut(): a rejected fingerprint is a person who could not prove who they are just now, not a person who logged out. The token stays, the password form opens, and the user finishes the sign-in. Opt-in (streetbite_biometric_sign_in) is stored on-device rather than in Firestore because it describes the handset: the same account on a tablet with no enrolled finger must not inherit an opt-in it can never satisfy.

openBiometricGate() دالة واحدة تستعملها البوّابتان: زر الصورة على الرئيسية الذي يحرس شاشة الملف الشخصي، وشاشة الدخول عند الإقلاع البارد. وسياستها: النجاح يستدعي onUnlocked، وكل شيء آخر يعرض ورشة تشرح السبب، مع «المتابعة بلا بصمة» حين يكون bypassAllowed صحيحًا. وتُقرَأ سلسلة reason من context قبل await، ويُحرَس الناتج بـcontext.mounted لأن طلب نظام التشغيل قد يبقى أطول من عمر الودجة.

وأهم قرار هو ما تفعله البصمة الفاشلة بالجلسة. فلا تستدعي AuthCubit.fallBackToPassword() signOut() عن قصد: بصمة مرفوضة شخص لم يستطع إثبات من يكون الآن، لا شخص سجل الخروج. فيبقى الرمز، ويُفتح نموذج كلمة المرور، ويُكمل المستخدم دخوله. وتُخزَّن الموافقة (streetbite_biometric_sign_in) على الجهاز لا في Firestore لأنها تصف الهاتف: الحساب نفسه على لوحي بلا بصمة مسجّلة لا يرث موافقة لا يستطيع الوفاء بها.

Prompt flagsأعلام طلب البصمة

biometricOnly: false keeps a device that has no fingerprint sensor unlockable with its own PIN. persistAcrossBackgrounding: true retries instead of failing when the user switches apps mid-scan. And there is no useErrorDialogs any more — the plugin stopped painting native error dialogs, so every failure mode is classified in BiometricService._classify and shown through the app's own ARB-backed UI. That is an improvement in both directions: the platform's English-only dialog cannot be localised, and this one can.

يبقي biometricOnly: false الجهازَ الذي لا حساس بصمة فيه قابلًا للفتح برقمه السري. ويعيد persistAcrossBackgrounding: true المحاولة بدل الفشل حين يبدّل المستخدم التطبيق أثناء المسح. ولا وجود لـuseErrorDialogs بعد الآن: توقفت الإضافة عن رسم ورش أخطاء أصلية، فتُصنَّف كل حالة فشل في BiometricService._classify وتُعرض في واجهة التطبيق بمفاتيح ARB. وهو تحسّن في الاتجاهين: فلا يمكن تعريب ورشة النظام الإنجليزية، ويمكن تعريب هذه.

Secrets and the buildالأسرار والبناء

Three files are gitignored and none of them is in the repository history: android/key.properties (the Maps key), android/app/google-services.json, and ios/Runner/GoogleService-Info.plist. The manifest reads ${MAPS_API_KEY}, filtered from key.properties with an empty default, so a fresh clone still builds — it just shows MapErrorBoundary until a key is supplied. The release build type uses signingConfig = debug, which is honest for coursework and wrong for a store submission.

The only credential in the repository is deliberate: the seeded QA account yasmine@streetbite.app / StreetBite123, created so the Appium suite and a marker on a fresh clone can sign in without a human. It is the demo fallback account, not a real user.

ثلاثة ملفات مستثناة من git وليس أي منها في تاريخ المستودع: android/key.properties (مفتاح الخرائط)، وandroid/app/google-services.json، وios/Runner/GoogleService-Info.plist. ويقرأ البيان ${MAPS_API_KEY} المرشَّح من key.properties مع افتراض فارغ، فيبني الاستنساخ الجديد نفسه — ويعرض MapErrorBoundary فقط حتى يُعطى مفتاح. ونوع البناء النهائي يستعمل signingConfig = debug، وهو صدق في مشروع دراسي وخطأ في تسليم متجر.

ووحيد بيانات الاعتماد في المستودع مقصود: حساب ضبط الجودة المزروع yasmine@streetbite.app / StreetBite123، أُنشئ حتى يستطيع حزمة Appium ومستخدم على استنساخ جديد الدخول بلا إنسان. وهو حساب الرجوع التجريبي لا مستخدم حقيقي.

Privacy, and one dead-end worth namingالخصوصية، وطريق مسدود يستحق الذكر

There is no analytics package, no crash reporter, no advertising ID and no telemetry of any kind: the only outbound traffic is TheMealDB, Firebase Auth and Firestore. Photos are picked and uploaded per the user's action, never read in bulk.

One declared affordance does less than it looks like. The manifest registers a VIEW intent filter with android:scheme="streetbite" and the comment calls it streetbite://qa/reset, used by the Appium suite to relaunch with a clean state — but nothing in lib/ parses that URI. Its real effect is that Android recreates the activity, so the app restarts from the splash. That is enough for the suite today, but the path is not handled and should not be described as a working deep link.

لا حزمة تحليلات، ولا مراسل أعطال، ولا معرّف إعلاني، ولا قياس عن بُعد على أي نحو: فكل صادِر هو MealDB وFirebase Auth وFirestore. وتُلتقَط الصور وتُرفَع بفعل المستخدم، لا تُقرَأ بالجملة أبدًا.

وأداة معلنة واحدة تفعل أقل مما تبدو. يبيان البيان VIEW بمفتاح معرِّف android:scheme="streetbite" ويسمّيه التعليق streetbite://qa/reset تستعمله حزمة Appium لإعادة الإقلاع بحالة نظيفة — لكن لا شيء في lib/ يحلّل هذه المعرِّفات. وأثره الحقيقي أن يعيد أندرويد إنشاء النشاط، فيبدأ التطبيق من شاشة البداية. وهذا يكفي الحزمة اليوم، لكن المسار غير معالج فينبغي ألا يُوصف بأنه رابط عميق يعمل.
