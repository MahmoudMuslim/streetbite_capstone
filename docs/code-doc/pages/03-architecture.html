03 · Architecture03 · المعمارية

The app is split into four layers. The dependency rule is the whole point: an import arrow may only point inwards. presentation may know domain, domain may know core, and data implements domain interfaces. domain contains zero package:flutter imports — verified across all 33 of its files — which is what lets the business rules run in a plain Dart VM with no widget tree.

ينقسم التطبيق إلى أربع طبقات. قاعدة التبعيات هي الفكرة كلها: سهم الاستيراد يشير إلى الداخل فقط. يحق لـ presentation أن تعرف domain، ويحق لـ domain أن تعرف core، وتُنفذ طبقة data واجهاتِ domain. لا تحتوي domain على أي استيراد من package:flutter — وهو أمر مُتحقَّق منه في ملفاتها الـ33 جميعًا — وهذا ما يسمح لقواعد العمل بأن تعمل في مفسر Dart عادي بلا شجرة Widgets.

presentation/ Widgets, screens, Blocs/Cubits, router, theme glue. Knows states and use cases, nothing else. الـ Widgets والشاشات و Blocs/Cubits والموجّه ووصلات الثيم. تعرف الحالات وحالات الاستخدام فقط.
domain/ Entities, repository interfaces, 20 use cases. Pure Dart — no Flutter, no Firebase, no Dio. الكيانات وواجهات المستودعات و20 حالة استخدام. Dart خالصة: بلا Flutter ولا Firebase ولا Dio.
data/ Models, data sources, repository implementations, the Firestore and biometric services. Owns every SDK import. النماذج ومصادر البيانات وتطبيقات المستودعات وخدمتا Firestore والبصمة. تملك كل استدعاءات SDK.
core/ Cross-cutting primitives: Either, Failure, UseCase, constants, the Dio wrapper, theme, validators. أدوات عرضية مشتركة: Either وFailure وUseCase والثوابت ولفّة Dio والثيم ودوال التحقق.

A tap, end to endضغطة واحدة من البداية إلى النهاية

Pressing + on a meal card is the shortest path through all four layers, so it is the clearest way to watch the rule work:

الضغط على + في بطاقة طبق هو أقصر مسار عبر الطبقات الأربع، وهي أوضح طريقة لمشاهدة القاعدة وهي تعمل:

1 · widgetCartLineAction tap handlerمعالج الضغط في CartLineAction
2 · eventCartBloc.add(CartItemAdded(meal))CartBloc.add(CartItemAdded(meal))
3 · use caseAddToCart(AddToCartParams(…)) — synchronous, pureAddToCart — متزامنة ونقية
4 · totalsCalculateOrderTotals rebuilds the moneyCalculateOrderTotals تعيد حساب المبلغ
5 · stateemit(CartUpdated(items, totals, lastAdded))emit(CartUpdated(…))
6 · UIBlocBuilder repaints badge, list and summary; BlocListener shows one SnackBarيُعيد BlocBuilder رسم الشارة والقائمة والملخص، ويعرض BlocListener رسالة واحدة

Checkout continues the same chain into the data layer: CartCheckoutRequested → PlaceOrder → OrderRepository (interface) → OrderRepositoryImpl → FirestoreService.writeToSubCollection(). The Bloc never imports Firestore and never learns a collection path: the only place orders/{uid}/items is spelled out is the gateway.

ويستمر إتمام الطلب في السلسلة نفسها إلى طبقة البيانات: CartCheckoutRequested ثم PlaceOrder ثم OrderRepository (واجهة) ثم OrderRepositoryImpl ثم FirestoreService.writeToSubCollection(). لا يستورد الـ Bloc Firestore أبدًا ولا يعرف اسم أي مجموعة، والمكان الوحيد الذي يُكتب فيه المسار orders/{uid}/items هو بوابة Firestore.

SOLID, and where each letter actually shows upمبادئ SOLID وأين يظهر كل حرف فعليًا

Principle Concrete evidence in this codebaseالدليل الملموس في هذا المشروع
SRP — single responsibility CalculateOrderTotals only does arithmetic; CartBloc only orchestrates; AuthLocalDataSource only reads and writes prefs.CalculateOrderTotals تحسب فقط، وCartBloc تنسق فقط، وAuthLocalDataSource تقرأ التفضيلات وتكتبها فقط.
OCP — open for extension, closed for modification A new payment method is a new class implementing PaymentMethod; the checkout screen and the order model do not change.أسلوب دفع جديد يعني صنفًا جديدًا ينفذ PaymentMethod دون تعديل شاشة الطلب ولا نموذج الطلب.
LSP — Liskov substitution CashPayment and CardPayment are interchangeable behind the interface; OrderModel rehydrates either from one type field.يمكن تبديل CashPayment وCardPayment خلف الواجهة، ويعيد OrderModel بناء أيهما من حقل type واحد.
ISP — interface segregation PaymentMethod exposes three getters and one method. Every repository interface has between two and four members.تكشف PaymentMethod عن ثلاثة مجتلبات ودالة واحدة، وكل واجهة مستودع بين عضوين وأربعة أعضاء.
DIP — dependency inversion Every Cubit and Bloc takes abstract use cases in its constructor, and injection.dart is the only file that names a concrete class.كل Cubit وBloc يستقبل حالات استخدام مجردة في بنائه، وinjection.dart هو الملف الوحيد الذي يسمي صنفًا ملموسًا.

One documented exception to the dependency ruleاستثناء واحد موثق لقاعدة التبعيات

presentation → data

Three files — biometric_gate.dart:4, biometric_login_screen.dart:7 and settings_screen.dart:12 — import data/services/biometric_service.dart to read the BiometricResult variants (success, failure, cancelled, notEnrolled, unavailable, lockedOut). A biometric outcome is a property of the handset, not a business rule, so inventing a domain type for it would be a lie. The cost: these are the only three UI files bound to the service class rather than to a domain abstraction.

ثلاثة ملفات — biometric_gate.dart:4 وbiometric_login_screen.dart:7 وsettings_screen.dart:12 — تستورد data/services/biometric_service.dart لقراءة احتمالات BiometricResult (success، وfailure، وcancelled، وnotEnrolled، وunavailable، وlockedOut). نتيجة البصمة صفة في الجهاز وليست قاعدة عمل، لذا اختراع نوع في Domain لها يكون تمثيلًا خاطئًا. والثمن: هذه هي الملفات الثلاثة الوحيدة في الواجهة المرتبطة بصنف الخدمة لا بتجريد في Domain.
