StreetBite code documentation · §14 Build & release

StreetBite code documentation · Part I · Section 14 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 14 من 18 · الفهرس الكامل

14 · Build & release14 · البناء والإصدار

StreetBite ships one artefact: an Android APK. The repository still carries the iOS, macOS, Windows, Linux and Web scaffolding Flutter generates, but nothing in the project targets them — no Apple developer settings, no bundle identifiers tuned, no web manifest. The honest framing is Android-only, and the practical consequence is that platform churn from flutter create under ios/ should be reverted, not committed.

The version is 1.0.0+3 in pubspec.yaml (versionName / versionCode), and both are handed to Gradle through flutter.versionName / flutter.versionCode, so the Dart file is the single place a release is bumped.

يصدَّر StreetBite في مُخرَج واحد: APK لأندرويد. ولا يزال المستودع يحمل هياكل iOS وmacOS وWindows وLinux والويب التي يولّدها Flutter، لكن لا شيء في المشروع يستهدفها — لا إعدادات مطوّري Apple، ولا معرّفات حزمة معدَّلة، ولا manifest للويب. والتصنيف الصادق هو أندرويد فقط، وأثره العملي أن أي تغيير منصات من flutter create تحت ios/ يُرجَع عنه ولا يُلتزَم به في git.

والإصدار 1.0.0+3 في pubspec.yaml (اسم الإصدار ورمزه)، وكلاهما يوصل إلى Gradle عبر flutter.versionName وflutter.versionCode، فملف Dart هو الموضع الوحيد الذي يُرفع فيه الإصدار.

Three of those numbers exist because of other people's code, and the build file says so. compileSdk = 36 is chosen because several bundled plugins (maps, image_picker, local_auth) already target 36, and compiling against the highest keeps them compatible with our own floor. minSdk = 24 is the practical floor for Play integrity checks on a 2026 build, above the 23 that local_auth alone would demand. And targetSdk stays one behind compileSdk, which is the normal, deliberate gap.

The conditional Firebase plugin is the cleverest line in the file. The Google Services Gradle plugin hard-fails when google-services.json is missing — which would make a fresh clone un-buildable, since that file is git-ignored. So it is applied only when the file exists:

if (file("google-services.json").exists()) {
  apply(plugin = "com.google.gms.google-services")
}

A contributor who clones the repository and runs flutter run therefore gets a working app in on-device fallback mode (§07); a contributor who drops in a real google-services.json silently gets Firebase Auth and Firestore, with no build file edit at all. That is the same degrade-instead-of-abort principle that main() follows at runtime, applied to the build.

ثلاثة من هذه الأرقام موجودة بسبب كود الآخرين، وملف البناء يقول ذلك. فـ compileSdk = 36 اختير لأن حزمًا مرفقة (الخرائط، ومنتقي الصور، والمصادقة البيومترية) تستهدف 36 أصلًا، والبناء مقابل الأعلى يبقيها متوافقة مع حدّنا الأدنى. وminSdk = 24 هو الأرض العملية لفحوص سلامة Play في بناء 2026، فوق 23 الذي تطلبه local_auth وحدها. ويبقى targetSdk خلف compileSdk بواحد، وهو الفارق المألوف المقصود.

إضافة Firebase الشرطية هي أذكى سطر في الملف. فإضافة Google Services الخاصة بـ Gradle تفشل بعنف حين يغيب google-services.json — ما يجعل الاستنساخ الجديد غير قابل للبناء، إذ أن هذا الملف مستثنى من git. لذا تُطبَّق فقط إن وُجد الملف، بالكود المبيّن أعلاه. فيحصل من يستنسخ المستودع ويشغّل flutter run على تطبيق عامِل في وضع التحوّل المحلي (§07)؛ ومن يضع google-services.json حقيقيًا يحصل على Auth وFirestore بصمت، دون تحرير ملف بناء إطلاقًا. وهذا هو مبدأ التدهور بدل الإجهاض الذي يسلكه main() أثناء التشغيل، مطبَّقًا على البناء.

Gradle tuning that is Windows-specificضبط Gradle خاص بويندوز

android/gradle.properties carries four deliberate edits on top of the Flutter template:

  • kotlin.incremental=false and kotlin.compiler.execution.strategy=in-process — Kotlin's memory-mapped incremental caches (.tab files) cannot be closed on Windows when an antivirus or the Search index holds a handle, failing the build with "Could not close incremental caches". Disabling incremental compilation sidesteps it; the cost is a few seconds per plugin module.
  • android.nonTransitiveRClass=true — the release is a single-ABI beta, so per-ABI splitting would only multiply build time.
  • android.nonFinalResIds=true — required for R8's optimised resource shrinking.
  • JVM args sized for this project: -Xmx8G with a 4 GB metaspace cap.

The release build type enables isMinifyEnabled and isShrinkResources with proguard-android-optimize.txt plus a project proguard-rules.pro that keeps the Flutter engine's entry points, the Play Services and Firebase classes (resolved reflectively), and silences the unused Play Core reference.

يحمل android/gradle.properties أربعة تعديلات مقصودة فوق قالب Flutter:

  • kotlin.incremental=false وkotlin.compiler.execution.strategy=in-process — لا يمكن إغلاق تخزين كوتلن التزايدي المعيَّن بالذاكرة (ملفات .tab) على ويندوز حين يحفظ مضادّ الفيروسات أو فهرس البحث مقبضًا، فيفشل البناء بـ «تعذّر إغلاق التخزين التزايدي». وعطّل هذا التزايدي يتجاوز المشكلة؛ وثمنها ثوانٍ قليلة لكل ملحق.
  • android.nonTransitiveRClass=true — إصدار تجريبي ببنية معمارية واحدة للعتاد، فتقسيم لكل بنية يضاعف زمن البناء وحسب.
  • android.nonFinalResIds=true — مطلوب لتقليص R8 المحسَّن للموارد.
  • وسائط JVM على قدر المشروع: -Xmx8G مع سقف 4 غيغابايت للـ metaspace.

ويُفعّل نمط الإطلاق isMinifyEnabled وisShrinkResources مع proguard-android-optimize.txt وملف proguard-rules.pro خاص بالمشروع يبقي نقاط دخول محرّك Flutter، وفئات Play Services وFirebase (لأنها تُحلّ بالانعكاس)، ويُخرس مرجع Play Core غير المستخدم.

Signing is debug, and the file admits it. signingConfig = signingConfigs.getByName("debug") inside the release block, with a comment giving the exact keytool command to generate an upload key before a real Play release. This is a defensible choice for a capstone distributed through Firebase App Distribution — where an internal key would break the out-of-the-box build for every reviewer — but it is not a Play Store configuration, and the documentation should not imply that it is.

The build is repeatable without secrets because manifestPlaceholders["MAPS_API_KEY"] is read from android/key.properties with an empty default, and the repository ships key.properties.example with the three-line copy-and-fill instructions. Absent a key the app still compiles, installs and runs; only the vendor map degrades (§11).

والتوقيع للتصحيح، والملف يقرّ بذلك. signingConfig = signingConfigs.getByName("debug") داخل كتلة release، مع تعليق يعطي أمر keytool الحرفي لتوليد مفتاح رفع قبل إطلاق Play حقيقي. وهذا اختيار يجوز الدفاع عنه لمشروع تخرّج يُوزَّع عبر Firebase App Distribution — حيث كان مفتاح داخلي سيكسر البناء الجاهز لكل مُراجِع — لكنه ليس إعدادًا للنشر في متجر Play، ولا يجب أن توحي الوثيقة بأنه كذلك.

ويكون البناء قابلًا للتكرار بلا أسرار لأن manifestPlaceholders["MAPS_API_KEY"] يُقرأ من android/key.properties بـافتراضي فارغ، ويصدّر المستودع key.properties.example مع ثلاث أسطر للنسخ والملء. وبلا مفتاح يظل التطبيق يُصرَّف ويُثبَّت ويعمل؛ خريطة البائعين وحدها تتدهور (§11).

Firebase, rules, and one stale referenceFirebase والقواعد ومرجعٌ بائت

firebase.json and firestore.rules are committed; google-services.json and ios/Runner/GoogleService-Info.plist are git-ignored. The rules file is the artefact that closed SB-114: without it, every Firestore read and write returned PERMISSION_DENIED while Auth kept working, so three screens failed and the app looked "mostly fine". The whole rule set is one idea — isOwner(uid), with the uid inside the path (users/{uid}, users/{uid}/favourites/{mealId}, orders/{uid}/items/{orderId}) — so orders are deliberately not a shared collection, because a query for all orders would need a rule that cannot distinguish rows. Anything unmatched is denied, so a new collection fails closed.

Runtime initialisation is Firebase.initializeApp() with no options argument (injection.dart:336), i.e. it relies entirely on the native google-services.json.

firebase.json وfirestore.rules ملتزَمان في git؛ و google-services.json وios/Runner/GoogleService-Info.plist مستثنيان. وملف القواعد هو ما أغلق SB-114: بدونه كانت كل قراءة وكتابة في Firestore تُعيد PERMISSION_DENIED بينما يستمر Auth في العمل، فتفشلت ثلاث شاشات وبدا التطبيق «سليمًا في الغالب». ومجموعة القواعد كلها فكرة واحدة — isOwner(uid) — والمعرّف داخل المسار (users/{uid}، users/{uid}/favourites/{mealId}، orders/{uid}/items/{orderId}) — فالطلبات ليست مجموعة مشتركة عن قصد، لأن استعلام كل الطلبات يحتاج قاعدة لا تستطيع التمييز بين الصفوف. وكل غير مطابق مرفوض، فمجموعة جديدة تفشل مغلقة.

وبادئ التشغيل هو Firebase.initializeApp() بلا وسائط (injection.dart:336)، أي أنه يعتمد كاملًا على google-services.json الأصلي.

Two build-time residues, recorded rather than hidden. (1) firebase.json still lists lib/firebase_options.dart under its flutter.dart key, but that file was removed during the dead-code pass (commit cdc93ee) — nothing imports it, because initialisation never used it. The reference is stale, not harmful, and cleaning it is a one-line edit. (2) cupertino_icons is declared in pubspec.yaml and never used: the app ships Android only and no Cupertino widget is instantiated. Neither is a defect, but both are the kind of claim a report should be able to check rather than assert. بقاياان في البناء، مسجَّلة لا مخفيّة. (1) لا يزال firebase.json يذكر lib/firebase_options.dart تحت مفتاح flutter.dart، لكن هذا الملف أُزيل في جولة الكود الميت (اللزمة cdc93ee) — لا أحد يستورده، لأن التهيئة لم تستخدمه قط. والمرجع بائت لا ضارّ، وتنظيفه سطر واحد. (2) وcupertino_icons معلن في pubspec.yaml ولا يُستخدم أبدًا: التطبيق يصدَّر لأندرويد فقط ولا تُنشَأ أي ودجة Cupertino. ولا هذا ولا ذاك عيب، لكنهما من نوع الادعاءات الذي يجب أن يستطيع التقرير التحقق منها لا الجزم بها.

Assets, icons and the lint gateالأصول والأيقونات وبوابة التدقيق

The flutter block in pubspec.yaml is deliberately tiny: uses-material-design: true, generate: true (which is what makes flutter run rebuild the localisation classes), and a single asset folder, assets/images/, holding the three launcher-icon bitmaps. The 1024 px master files live in assets/icon/ — outside the declared folder on purpose, with a comment explaining that declaring it would ship the masters inside the APK. They are generated by scripts/make_launcher_icons.py and packaged by flutter_launcher_icons.

Quality gates are two commands and no more: dart format . and flutter analyze. analysis_options.yaml is the untouched template — it includes package:flutter_lints/flutter.yaml and enables zero additional project rules, and it excludes build/ and every platform folder from analysis. So "No issues found" means "no lint errors under the standard Flutter ruleset", not "the project wrote and enforced its own rules". The three Python scripts under streetbite_capstone/scripts/ are the only custom tooling: make_launcher_icons.py, plus check_unused_arb.py and prune_arb.py which keep the 356 ARB entries (§10) free of dead keys.

There is no CI. No .github/ directory, no pipeline file anywhere in the repository. Every number in §13 comes from a command run by hand on one machine, which is stated here so it is not discovered later.

كتلة flutter في pubspec.yaml صغيرة عن قصد: uses-material-design: true، وgenerate: true (وهو ما يجعل flutter run يعيد بناء أصناف الترجمة)، ومجلد أصول واحد assets/images/ يحمل ثلاث صور للأيقونة. وملفات الأصل بحجم 1024 بكسل تعيش في assets/icon/ — خارج المجلد المعلن عن قصد، مع تعليق يشرح أن الإعلان كان سيضعها داخل APK. وتُولّدها scripts/make_launcher_icons.py وتُغلّفها إضافة flutter_launcher_icons.

وبوابتا الجودة أمران لا أكثر: dart format . وflutter analyze. و analysis_options.yaml قالب لم يُمسَّ — يضمّ package:flutter_lints/flutter.yaml ويُمكّن صفر قاعدة خاصة بالمشروع، ويستثني build/ وكل مجلدات المنصات من التحليل. فـ «لا مشاكل وجدت» تعني «لا أخطاء تدقيق تحت مجموعة قواعد Flutter القياسية»، لا «المشروع كتب قواعده وفرضها». والدوال Python الثلاث تحت streetbite_capstone/scripts/ هي الأداة الخاصة الوحيدة: make_launcher_icons.py، وcheck_unused_arb.py وprune_arb.py يُبقيان مفاتيح ARB الـ 356 (§10) خالية من الميت.

ولا CI أبدًا: لا مجلد .github/ ولا ملف مسار أنابيب في المستودع. وكل رقم في §13 من أمر شُغِّل يدويًا على آلة واحدة، ويُقال هذا هنا حتى لا يُكتشف متأخرًا.

From clone to phoneمن الاستنساخ إلى الهاتف

1 · Clone & configureflutter pub get — then optionally cp android/key.properties.example android/key.properties and drop in google-services.json ١ · استنساخ وإعداد: flutter pub get، ثم — اختيارًا — نسخ ملف الخصائص ووضع google-services.json
2 · Runflutter run — builds debug, installs, no Firebase or Maps key required ٢ · تشغيل: flutter run يبني نسخة التصحيح ويثبّتها، ولا يطلب مفتاح Firebase ولا خرائط
3 · Build the releaseflutter build apk --release → build/app/outputs/flutter-apk/app-release.apk (≈ 63 MB, R8-minified, debug-signed) ٣ · بناء الإطلاق: الأمر المذكور يُنتج APK نحو 63 ميغابايت، مُقلَّص بـ R8 وموقَّع للتصحيح
4 · Distributefirebase appdistribution:distribute …apk --testers … --release-notes … ٤ · التوزيع: أمر App Distribution مع المختبِرين وملاحظات الإصدار
5 · Verifyflutter test (99) · install on the handset · mvn -f automation/pom.xml test (6) ٥ · التحقق: الاختبارات التسعة والتسعون، ثم التثبيت على الهاتف، ثم ست حالات Appium

The two APKs in the working tree are useful evidence of what "release" costs here: app-debug.apk is 197 MB, app-release.apk is 63 MB — a 3.1× reduction that is minification, resource shrinking, and the absence of the debug service extension and observatory. Each sits beside a .sha1 file, which is what the Appium suite's install step can compare against a stale artefact (a lesson learned the hard way when the suite ran against an APK older than the code under test).

ملفا APK الموجودان في شجرة العمل دليل نافع على كلفة «الإطلاق» هنا: app-debug.apk وزنُه 197 ميغابايت، وapp-release.apk 63 ميغابايت — تقليص 3.1 مرّات مصدره التصغير، وتقليص الموارد، وغياب امتداد خدمة التصحيح وobservatory. وكل واحد بجانبه ملف .sha1، وهو ما تستطيع خطوة التثبيت في مجموعة Appium أن تقارن به مُخرَجًا بائتًا — درس استُخرج بالقوة حين شغّلت المجموعة على APK أقدم من الكود محلّ الاختبار.
