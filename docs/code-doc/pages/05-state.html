StreetBite code documentation · §05 State management

StreetBite code documentation · Part I · Section 05 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 05 من 18 · الفهرس الكامل

05 · State management05 · إدارة الحالة

State lives in eight places, all of them flutter_bloc objects. Seven are registered as lazy singletons and provided once at the root in app.dart; ProfileCubit is the exception — it is created by the Profile screen itself, since nothing outside that screen needs it. Seven are Cubits; exactly one is a Bloc.

The choice is reasoned per object, not by habit. A Cubit is right when the transitions are strictly sequential and no event needs an identifier, a debounce, or a concurrency transformer. AuthCubit restores, then logs in or signs up, then logs out — nothing else, so a Bloc would add ceremony without adding capability. CartBloc is a Bloc because checkout is a real transaction that can fail halfway and must keep the items it was built from.

تقع الحالة في ثمانية مواضع، وكلها كائنات flutter_bloc. سبعة منها مسجلة كمفردات كسولة ومهيأة مرة واحدة في الجذر داخل app.dart؛ وProfileCubit هو الاستثناء — تُنشئه شاشة الملف الشخصي بنفسها لأن شيئًا خارج تلك الشاشة لا يحتاجه. سبعة منها Cubits وواحد منها Bloc بالضبط.

الاختيار مدروس لكل كائن وليس بالعادة. الـ Cubit مناسب عندما تكون الانتقالات متتابعة صارمة ولا يحتاج أي حدث إلى معرّف أو تأجيل أو مُحوِّل تزامن. AuthCubit يستعيد الجلسة ثم يسجل الدخول أو ينشئ الحساب ثم يسجل الخروج — لا شيء غير ذلك، لذا كان الـ Bloc سيضيف طقوسًا بلا قدرة. أما CartBloc فهو Bloc لأن إتمام الطلب معاملة حقيقية قد تفشل في منتصفها ويجب أن تحتفظ بالأصناف التي بُنيت منها.

Sealed states make impossible screens impossibleالحالات المختومة تستحيل معها الشاشات المستحيلة

Every multi-state family is a sealed class, so a screen that switches over it gets a compile-time guarantee that all cases are handled — the same argument that made Either the error vehicle. Loading is a real state, not a boolean, which is why the Home feed can show a section-for-section shimmer skeleton (MealsLoading) and then the data (MealsLoaded) without the widget knowing any arithmetic.

Each state extends Equatable and declares props, so Bloc rebuilds compare by value. Two MealsLoaded with the same meals emit once, not twice.

كل عائلة متعددة الحالات هي sealed class، لذا أي شاشة تُجري switch عليها تحصل على ضمان وقت التصريف أن جميع الحالات معالَجة — وهي الحجة نفسها التي جعلت Either وسيلة نقل الأخطاء. التحميل حالة حقيقية لا منطقية، وهذا سبب قدرة التغذية الرئيسية على إظهار هيكل لامع قسمًا بقسم (MealsLoading) ثم البيانات (MealsLoaded) دون أن يعرف الـ Widget أي حساب.

كل حالة ترث Equatable وتُعلِن props، فتُقارَن إعادةُ البناء بالقيمة. حالتا MealsLoaded بأطباق متطابقة تُطلقان إشعارًا واحدًا لا اثنين.

Where the providers sit, and why it mattersأين تتموضع الـ Providers ولماذا يهم ذلك

app.dart wraps MaterialApp in a MultiBlocProvider that uses BlocProvider<T>.value for those seven — .value because the container owns them and no widget may dispose them. ThemeCubit and LocaleCubit are above MaterialApp and read by BlocBuilder around it, because they change MaterialApp's own configuration. That is what makes the dark-mode and EN/AR switches instant with no restart and no setState anywhere.

The five feature objects are also at the root on purpose: the cart badge in the Home AppBar and the item list on the Cart screen must read the same CartBloc, or they can disagree for a frame.

ملف app.dart يلفّ MaterialApp بـ MultiBlocProvider يستخدم BlocProvider<T>.value للسبعة الجذرية — و.value لأن الحاوية تملكها ولا يحق لأي Widget أن يُتلفها. ThemeCubit وLocaleCubit فوق MaterialApp ويقرأهما BlocBuilder حولها، لأنهما يغيّران إعداد MaterialApp نفسه. وهذا ما يجعل تبديل الوضع الداكن واللغة فوريًا بلا إعادة تشغيل وبلا setState في أي موضع.

والكائنات الخمسة الخاصة بالميزات في الجذر أيضًا عن قصد: شارة السلة في شريط الرئيسية وقائمة الأصناف في شاشة السلة يجب أن يقرآ نفس نسخة CartBloc، وإلا اختلفتا لإطار رسم واحد.

Builder versus Listenerالفرق بين Builder و Listener

BlocBuilder rebuilds widgets from state; BlocListener fires side effects. The app keeps them apart: transient messages never live in state that a builder renders. CartUpdated carries lastAdded, lastRemoved and justEmptied purely so a BlocListener can decide whether to show a SnackBar — and the Bloc, not the widget, owns the "was non-empty, now empty" comparison.

Because CartUpdated is Equatable on those extra fields, a repeated add of the same meal still produces a distinct state and the message still shows. That is the subtlety the three fields exist for.

BlocBuilder يعيد بناء الـ Widgets من الحالة، أما BlocListener فيُطلق التأثيرات الجانبية. يفصل التطبيق بينهما: الرسائل العابرة لا تعيش أبدًا في حالة يعرضها Builder. تحمل CartUpdated الحقول lastAdded وlastRemoved وjustEmptied فقط ليقرر BlocListener إن كان لإظهار رسالة — والـ Bloc لا الـ Widget هو من يملك مقارنة «كانت غير فارغة فأصبحت فارغة».

ولأن CartUpdated تُطبَّق Equatable على هذه الحقول الزائدة، فإن إضافة نفس الطبق مرتين تُنتج حالتين مختلفتين وتظهر الرسالة مرة أخرى. هذا هو التفصيل الدقيق الذي وُجدت لأجله الحقول الثلاثة.

Lazy tabs and the one deliberate warm-upالتبويبات الكسولة وتعبئة واحدة مقصودة

MainShellScreen keeps an IndexedStack plus a _built set, so a tab is not constructed until the user first opens it. The exception is the Orders tab: because OrdersCubit is a lazy singleton, the shell warms it in a post-frame callback once the Home screen is up, so the history is already in memory by the time the tab is opened. The cart survives a tab switch for the same reason — it lives in the container, not in a tab.

يحتفظ MainShellScreen بـ IndexedStack مع مجموعة _built، فلا يُبنى أي تبويب قبل أن يفتحه المستخدم أول مرة. الاستثناء تبويب الطلبات: لأن OrdersCubit مفردة كسولة، يعبّئها الهيكل في نداء بعد الإطار الأول بمجرد ظهور شاشة الرئيسية، فيكون السجل محمّلًا في الذاكرة حين يُفتح التبويب. وتنجو السلة من التنقل بين التبويبات للسبب نفسه — فهي تعيش في الحاوية لا في تبويب.

Anti-patterns this layer avoidsأساليب خاطئة تتجنبها هذه الطبقة

  • No Cubit talks to a repository; only a use case does.
  • No Bloc stores a BuildContext or a GlobalKey.
  • No widget performs money arithmetic — CalculateOrderTotals is the only formula.
  • No setState is used to mirror a Bloc; local StatefulWidget state is kept to genuine widget concerns (obscure toggles, text controllers, scroll position).
  • No error is swallowed: an AuthFailureState carries a key, and the UI must resolve it.
  • لا يخاطب أي Cubit مستودعًا؛ حالة الاستخدام وحدها تفعل.
  • لا يخزّن أي Bloc BuildContext ولا GlobalKey.
  • لا يجري أي Widget حسابات نقدية — CalculateOrderTotals هي الصيغة الوحيدة.
  • لا يُستخدم setState لمحاكاة Bloc؛ تقتصر حالة StatefulWidget المحلية على شواغل الـ Widget الحقيقية (إظهار كلمة المرور، ومتحكمات النص، ومواضع التمرير).
  • لا يُبتلع أي خطأ: تحمل AuthFailureState مفتاحًا، وعلى الواجهة ترجمته.
