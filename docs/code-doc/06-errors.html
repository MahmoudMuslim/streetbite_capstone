StreetBite code documentation · §06 Error handling

StreetBite code documentation · Part I · Section 06 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 06 من 18 · الفهرس الكامل

06 · Error handling06 · معالجة الأخطاء

This is the requirement the whole project is organised around: no unhandled exception anywhere. StreetBite gets there by refusing to use exceptions as a cross-layer protocol. An exception is allowed inside one layer, must be caught at the boundary of that layer, and leaves it as a value — a Failure inside the left branch of an Either.

هذا هو المطلب الذي نُظِّم حوله المشروع كله: لا استثناء غير معالَج في أي مكان. يحقق StreetBite ذلك بأن يرفض استخدام الاستثناءات بروتوكولًا بين الطبقات. الاستثناء مسموح داخل طبقة واحدة، ويجب التقاطه عند حدّها، ويخرج منها قيمةً — وهو Failure في الفرع الأيسر من Either.

The three-step contractالعقد ذو الخطوات الثلاث

1 · data sourceA plugin throws (DioException, FirebaseException, PlatformException). The wrapper rethrows one of three app exceptions.ترمي الإضافة استثناءً (DioException، وFirebaseException، وPlatformException)، ويعيد الغلاف الرمي بأحد ثلاثة استثناءات خاصة بالتطبيق.
2 · repositoryCatches it and returns Left(someFailure). This is the boundary — nothing passes through uncaught.تلتقطه وتُعيد Left(someFailure). هذا هو الحدّ: لا شيء يعبر غير ملتقَط.
3 · Cubit / Blocresult.fold(onFailure, onSuccess) — the compiler forces both branches. The failure branch emits a state that carries messageKey.تُطوي الحالة result.fold(onFailure, onSuccess) — ويُجبر المترجم فرعي الاثنين. فرع الخطأ يطلق حالة تحمل messageKey.
4 · widgetThe key is resolved by context.trKey(...) into an English or Arabic sentence and shown by AppErrorView or a SnackBar.يُحلّ المفتاح بـ context.trKey(...) إلى جملة إنجليزية أو عربية ويعرضه AppErrorView أو رسالة قصيرة.

Either — why a value and not a throwEither — لماذا قيمة لا رمية

core/error/either.dart is a 62-line sealed type: Left<L, R> for the failure, Right<L, R> for the success, and three members — fold, map and valueOrNull. The file's own doc comment states the argument: exceptions are invisible to the type system, so a repository can forget one and the compiler stays quiet, which is exactly how an unhandled exception reaches production. With a sealed result type the caller cannot ignore the failure branch.

map is what lets a use case refine a result without unwrapping it — GetOrderHistory uses it to re-resolve every stored order status against the clock while leaving a Left untouched.

ملف core/error/either.dart نوع مختوم من 62 سطرًا: Left<L, R> للخطأ، وRight<L, R> للنجاح، وثلاثة أعضاء فقط — fold وmap وvalueOrNull. يشرح تعليق الملف نفسه الحجة: الاستثناءات غير مرئية لنظام الأنواع، فيمكن لمستودع أن ينسى واحدًا ويظل المترجم صامتًا، وهذا بالضبط كيف يصل استثناء غير معالَج إلى الإنتاج. مع نوع نتيجة مختوم لا يستطيع المستدعي تجاهل فرع الخطأ.

ودالة map هي ما يسمح لحالة استخدام بتهذيب النتيجة دون فكّها — تستخدمها GetOrderHistory لإعادة حلّ حالة كل طلب مخزَّن مقابل الوقت، مع ترك أي Left كما هو.

Firebase Auth codes are translated, never forwardedرموز Firebase Auth تُترجَم ولا تُمرَّر

AuthRemoteDataSource.mapAuthError is a single exhaustive switch from a Firebase error code to an ARB key: invalid-email → authErrorInvalidEmail, email-already-in-use → authErrorEmailInUse, weak-password → authErrorWeakPassword, user-not-found → authErrorUserNotFound, too-many-requests → authErrorTooManyRequests, network-request-failed → authErrorNetwork, and everything else → authErrorUnknown. Both wrong-password and the newer unified invalid-credential land on authErrorWrongPassword, so the app shows one message whichever one Firebase happens to return.

That last key is load-bearing: AuthRepositoryImpl._isConnectivityFailure treats only authErrorNetwork and authErrorUnknown as a reason to fall back to the on-device store. A credential rejection is not connectivity, and falling back for it would let a wrong password succeed offline — a false pass that would have made the whole Appium suite meaningless.

يربط mapAuthError في AuthRemoteDataSource رمزَ Firebase واحدًا بمفتاح ARB واحد: invalid-email ← authErrorInvalidEmail، وemail-already-in-use ← authErrorEmailInUse، وweak-password ← authErrorWeakPassword، وuser-not-found ← authErrorUserNotFound، وtoo-many-requests ← authErrorTooManyRequests، وnetwork-request-failed ← authErrorNetwork، وكل ما عدا ذلك ← authErrorUnknown. وأمّا wrong-password وinvalid-credential — وهو الرمز الموحّد الجديد — فيتحوّلان معًا إلى authErrorWrongPassword، فلا يغير التطبيق رسالته أيّ الرمزين أرجعت Firebase.

وهذا المفتاح الأخير حامل للأثر: لا يعتبر AuthRepositoryImpl._isConnectivityFailure سوى authErrorNetwork وauthErrorUnknown سببًا للرجوع إلى المخزن المحلي. فرفض بيانات الاعتماد ليس انقطاع اتصال، والرجوع عنده كان ليجعل كلمة مرور خاطئة تنجح أثناء عدم الاتصال — نتيجة خاطئة كانت ستُفقد حزمة Appium معناها كله.

The last three netsالشِّباكَ الثلاث الأخيرة

  • Start-up: main() wraps dependency wiring in try, then verifies the graph with _isGraphWired(). A half-built container renders _StartupFailureApp — a plain screen with the exact fix printed on it — instead of crashing inside runApp, the one place Flutter has no recovery.
  • The map: MapErrorBoundary is an ErrorWidgetBuilder scope around the Google Maps widget. If the platform view fails to paint (a disabled API key, no GPU), only the map is replaced by MessagePanel; the rest of the screen survives.
  • Money: an empty basket produces no fees at all, so a failed checkout can never display "−$2.49" or a phantom delivery charge.
  • الإقلاع: يلفّ main() توصيل التبعيات في try ثم يتحقق من الشجرة بـ _isGraphWired(). فالحاوية نصف المبنية تعرض _StartupFailureApp — شاشة بسيطة تطبع الإصلاح المطلوب عليها — بدل الانهيار داخل runApp، وهو الموضع الوحيد في Flutter الذي لا رجوع فيه.
  • الخريطة: MapErrorBoundary نطاق ErrorWidgetBuilder حول أداة خرائط Google. وإذا فشل العرض الأصلي في الرسم (مفتاح API معطَّل، أو لا معالج رسومات) تُستبدل الخريطة وحدها بـ MessagePanel ويبقى بقية الشاشة.
  • المال: السلة الفارغة لا تُنتج أي رسوم، فلا يمكن لإتمام طلب فاشل أن يعرض «−$2.49» أو رسوم توصيل وهمية.
What a user can actually see · ما يراه المستخدم فعلًا

Three surfaces, all built on the same MessagePanel: AppLoadingView (waiting), EmptyStateView (nothing to show), AppErrorView (something failed, with a Retry button). A failure never shows a stack trace, a status code, or an English sentence in an Arabic UI.

ثلاثة أسطح، كلها مبنية على نفس MessagePanel: AppLoadingView (في الانتظار)، وEmptyStateView (لا شيء للعرض)، وAppErrorView (حدث خطأ، مع زر إعادة). ولا يعرض الفشل أبدًا تتبع مكدّس ولا رمز حالة ولا جملة إنجليزية في واجهة عربية.
