StreetBite code documentation · Part I · Section 12 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 12 من 18 · الفهرس الكامل

12 · Navigation12 · التنقّل

StreetBite navigates with the framework's own imperative API — Navigator.pushNamed and a route-name table — not with a router package. There is exactly one place where a name becomes a widget: AppRouter.resolve, wired as onGenerateRoute on the MaterialApp in app.dart:103 with initialRoute: AppRoutes.splash.

The consequence is a property the code relies on rather than a library feature: the graph is complete by construction. AppRoutes declares twelve names; the switch has twelve cases plus a default. A route name with no screen behind it cannot exist, because adding a constant without a case silently lands on the splash instead of throwing — which is the fail-safe a capstone wants, not a red crash screen.

يتنقّل StreetBite بواجهة الإطار الآمرة نفسها — Navigator.pushNamed وجدول أسماء المسارات — لا بحزمة موجِّه. وهناك موضع واحد فقط يتحوّل فيه الاسم إلى ودجة: AppRouter.resolve، الموصول كـ onGenerateRoute في MaterialApp داخل app.dart:103 مع initialRoute: AppRoutes.splash.

والنتيجة خاصية يعتمد عليها الكود لا ميزة مكتبة: اكتمال الرسم بالبناء. يُعلن AppRoutes عن اثني عشر اسمًا، وفي switch اثنتا عشرة حالة وdefault. فلا يمكن وجود اسم مسار بلا شاشة خلفه، لأن إضافة ثابت دون حالة يهبط على شاشة البداية بصمت بدل أن يستثني — وهو الفشل الآمن الذي يناسب مشروع التخرّج، لا شاشة انهيار حمراء.

The argument contract. resolve opens with settings.arguments as List? ?? const [] and every typed value is read positionally — args.first! as MealEntity. Flutter's own contract for a generated route is a list whose first element is the payload, so a caller writes arguments: [meal], never arguments: meal. That is the one convention a new screen must learn before it can be reached.

Two screens accept a missing argument and synthesise a placeholder: _MissingMeal (an MealEntity with every field empty and price: 0) and _placeholderOrder(). The order placeholder keeps id: '' on purpose — the screen keys its "nothing to show" branch off that empty id, so a bad deep link lands on the empty state rather than on a receipt with a fabricated number and timestamp. It cannot be const because OrderEntity carries a DateTime, and it is given CashPayment and OrderStatus.past so the placeholder satisfies the entity's own non-null fields.

عقد الوسائط. يفتتح resolve بـ settings.arguments as List? ?? const []، وتُقرأ كل قيمة مُصنَّفة بالترتيب — args.first! as MealEntity. وعقد Flutter نفسه للمسار المولَّد هو قائمة أوّل عنصرها هو الحمولة، فيكتب المستدعي arguments: [meal] ولا يكتب أبدًا arguments: meal. وهذا هو الاصطلاح الواحد الذي على أي شاشة جديدة أن تتعلّمه قبل أن يُتوصَّل إليها.

وشاشتان تقبلان الوسيط الناقص وتُركّبان بديلًا: _MissingMeal (كيان MealEntity بكل حقوله فارغة وprice: 0) و_placeholderOrder(). وأما بديل الطلب فيُبقي id: '' عن قصد — فالشاشة تُفرّع حالتها «لا شيء يُعرض» اعتمادًا على هذا المعرّف الفارغ، وهكذا يهبط الرابط الخارجي الخاطئ على الحالة الفارغة لا على إيصال برقم ووقت مُختلَقين. ولا يمكن أن يكون const لأن OrderEntity يحمل DateTime، ويأخذ البديل CashPayment وOrderStatus.past حتى يُلبي حقول الكيان غير القابلة للعدم.

Every screen arrives through the same transitionكل شاشة تصل عبر الانتقال نفسه

AppPageRoute<T> extends PageRouteBuilder<T> and is the route type the router hands back for all twelve names. Its buildTransitions is a 320 ms Curves.easeOutCubic fade wrapped around a SlideTransition from Offset(0, 0.035) — a 3.5 % upward drift, visible but never showy. Forward and reverse durations are the same constant, so backing out of a screen costs exactly as much time as entering it.

The reason to subclass rather than use MaterialPageRoute is stated in the file: because it is a real PageRoute, the meal-card Hero flights still work. A fade alone would have killed the photo flight between the card and the detail screen.

Both ends of that flight carry the same tag, 'meal-image-${meal.id}, in three widgets — meal_card.dart:59, meal_banner_page.dart:56 and meal_details_screen.dart:68 — so a tap on a home feed card, a hot-offers banner, or a search-sheet row all animate into the detail photo. The tag is keyed on the meal id, which is why two cards can be on screen at once without the flight jumping between them.

AppPageRoute<T> يرث PageRouteBuilder<T> — وهو نوع المسار الذي يعيده الموجِّه للأسماء الاثني عشر جميعًا. وbuildTransitions عنده عبارة عن تلاشٍ 320 ملّي ثانية بمنحنى Curves.easeOutCubic ملفوف حول SlideTransition من Offset(0, 0.035) — انزياح صاعد بنسبة 3.5 %، ظاهر دون تكلّف. والمدة الأمامية والخلفية ثابت واحد، فالخروج من شاشة يكلّف الوقت نفسه الذي تكلفه دخولها.

والسبب في التوريث بدل MaterialPageRoute مذكور في الملف: لأنه PageRoute حقيقي، فإن طيران Hero الخاص ببطاقات الأطباق يعمل كما هو. وكان التلاشي وحده ليقتل طيران الصورة بين البطاقة وشاشة التفاصيل.

وطرفا ذلك الطيران يحملان الوسم نفسه 'meal-image-${meal.id} في ثلاث ودجات — meal_card.dart:59 وmeal_banner_page.dart:56 وmeal_details_screen.dart:68 — فتتحرّك نقرة بطاقة في التغذية الرئيسية، أو نقرة بانر العروض الساخنة، أو نقرة سط في ورقة البحث، كلها نحو صورة التفاصيل. والوسم مربوط بمعرّف الطبق، وهذا سبب قدرة بطاقتين على الظهور معًا دون أن يقفز الطيران بينهما.

The four-tab shell: state that survives a tab switchالهيكل ذو التبويبات الأربعة: حالة تنجو من تبديل التبويب

MainShellScreen is one route that owns four screens — Home, Browse, Orders, Profile — through an IndexedStack, not by rebuilding on each switch. An IndexedStack keeps every child in the tree and shows one, so the Home feed remembers its scroll offset and its PageView index, and coming back from the Cart does not re-trigger a network fetch. On a phone a user bounces between tabs dozens of times a session; that is the reason for the widget choice, not aesthetics.

The four children are handed through _tab(index, screen), which is a one-line _built.putIfAbsent(index, () => screen) over a <int, Widget>{} map. It looks redundant — the const constructors make building cheap — but its job is to make the intent explicit and to be the single place where a future non-const tab would become lazy. Tab indices also exist as named constants on AppRoutes (tabHome 0 … tabProfile 3) plus MainShellScreen.ordersTabIndex = 2 as a static const, because the order-confirmation screen needs that number without importing the shell's internals.

initState schedules one thing after the first frame: read AuthCubit, and if the session is authenticated call OrdersCubit.load(uid). That warms the orders cache so the Orders tab renders instantly on the first tap instead of showing a spinner the user has to wait out.

MainShellScreen مسار واحد يملك أربع شاشات — الرئيسية، التصفّح، الطلبات، الملف — عبر IndexedStack، لا بإعادة البناء عند كل تبديل. ويُبقي IndexedStack كل الأبناء في الشجرة ويعرض واحدًا، فتتذكر التغذية الرئيسية موضع تمريرها ومفهرس PageView، والعائد من السلة لا يعيد تشغيل طلب شبكة. وعلى الهاتف يتنقّل المستخدم بين التبويبات عشرات المرّات في الجلسة، وهذا هو سبب اختيار الودجة لا المظهر.

ويُمرَّر الأبناء الأربعة عبر _tab(index, screen)، وهي سطر واحد _built.putIfAbsent(index, () => screen) فوق قاموس <int, Widget>{}. وتبدو زائدة — فالبُنَيات الثابتة (const) تجعل البناء رخيصًا — لكن وظيفتها جعل النية صريحة، وأن تكون الموضع الوحيد الذي يصبح فيه تبويب غير ثابت كسولًا عند إضافته لاحقًا. ومؤشرات التبويبات موجودة أيضًا كثوابت مُسمَّاة على AppRoutes (tabHome 0 … tabProfile 3) مع MainShellScreen.ordersTabIndex = 2 كـ static const، لأن شاشة تأكيد الطلب تحتاج هذا الرقم دون استيراد داخلَيّات الهيكل.

ويرتّب initState شيئًا واحدًا بعد الإطار الأول: قراءة AuthCubit، وإن كانت الجلسة مُوثَّقة يُستدعى OrdersCubit.load(uid). وهذا يُسخّن مخزن الطلبات حتى يظهر تبويب الطلبات فور أول نقر بدل أن يُعرض دوّارة انتظار.

Two chrome branches, one body — the shell branches on AppGlassTokens.enabledOf(context): under glass the same IndexedStack is hosted by a GlassScaffold with a refractive GlassTabBar, otherwise by a plain Scaffold with a Material NavigationBar (whose destinations carry ValueKey('nav_home' | 'nav_browse' | 'nav_orders' | 'nav_profile') for widget tests). This is the one place in the app where the glass look changes structure, not just palette — navigation chrome is what the material was designed for. فرعًا واجهة، جسم واحد — يتفرّع الهيكل على AppGlassTokens.enabledOf(context): تحت الزجاج يُستضاف IndexedStack نفسه بـ GlassScaffold ومعها GlassTabBar انكساري، وإلا بـ Scaffold عادية و NavigationBar مادية (وجهاتها تحمل ValueKey باسم nav_home وnav_browse وnav_orders وnav_profile لاختبارات الودجات). وهذا الموضع الوحيد الذي يغيّر فيه مظهر الزجاج البنية لا اللوحة وحدها — فواجهة التنقّل هي ما صُمّم له هذا الخام.

Two details of the glass branch are non-obvious and are commented in the source. extendBody: true lets the feed run behind the floating capsule, which means the body no longer reserves room for it — so the shell republishes the capsule height as MediaQuery.padding.bottom using AppGlassTokens.bottomBarClearance (104 dp). Screens read that one value as scroll padding and stay correct under either look, because it is the same channel Material uses for a NavigationBar. And because GlassScaffold does not wrap its bottomBar in a Material, the tab labels would inherit MaterialApp's fallback style — monospace with a yellow double underline — so a DefaultTextStyle supplies the app's own bodyMedium with the decoration cleared, while the bar still layers its per-state colour, size and weight on top.

The status bar is pinned rather than set to auto: auto follows the device brightness, which can disagree with the in-app theme, so the style is chosen from Theme.of(context).brightness.

وتفصيلان في فرع الزجاج غير بديهيّين، وهما معلَّق عليهما في المصدر. فـ extendBody: true يسمح للتغذية بالمرور خلف الكبسولة العائمة، ما يعني أن الجسم لم يعد يحجز لها حيّزًا — لذلك يعيد الهيكل نشر ارتفاع الكبسولة على أنه MediaQuery.padding.bottom، آخذًا قيمته من AppGlassTokens.bottomBarClearance (104 نقطة). وتقرأ الشاشات هذه القيمة الواحدة كحشو تمرير وتبقى صحيحة تحت أيٍّ من المظهرين، لأنها القناة نفسها التي تستخدمها مادية لـ NavigationBar. ولأن GlassScaffold لا يلفّ bottomBar داخل Material، كانت تسميات التبويبات لترث الأسلوب الاحتياطي لـ MaterialApp — خطّ أحادي المسافة تحته خطّان أصفران — فيوفّر DefaultTextStyle أسلوب bodyMedium الخاص بالتطبيق بعد حذف الزخرفة، بينما يظلّ الشريط يطبّق لونه وحجمه ووزنه لكل حالة في طبقة أعلى.

وشريط الحالة مثبَّت لا auto: لأن auto يتبع سطوع الجهاز، وقد يخالف السمة داخل التطبيق، فيُختار الأسلوب من Theme.of(context).brightness.

Splash waits for two independent gates. SplashScreen refuses to navigate until both the entrance animation has run its minimum display time and AuthCubit.restore() has answered. Two flags are checked in _tryNavigate(), which is called from the animation delay and from the end of the restore — whichever finishes second performs the jump, so the user never sees a half-built screen or a splash that flickers before the verdict.

The destination is a pure function of the auth state: authenticated → home, AuthBiometricGate → biometricLogin, anything else → login. A gated session goes to the scan screen rather than the password form, because landing on Login after the device had already accepted the credentials would make the whole opt-in invisible. The jump itself builds the page by calling AppRouter.resolve(RouteSettings(name: route)) directly inside a 450 ms fade PageRouteBuilder — the router is a function, so the splash can reuse it without going through onGenerateRoute.

البداية تنتظر بابين مستقلّين. ترفض SplashScreen التنقّل حتى تعمل كلاهما: مدة العرض الدنيا للأنيميشن و ردّ AuthCubit.restore(). وعلمان يُفحصان في _tryNavigate() المستدعاة من تأخير الأنيميشن و من نهاية الاستعادة — فينفّذ القفز الثاني انتهاءً، فلا يرى المستخدم شاشة نصف مبنية ولا بداية تومض قبل الحكم.

والوجهة دالة خالصة في حالة المصادقة: مُوثَّق ← home، وAuthBiometricGate ← biometricLogin، وكل شيء آخر ← login. فالجلسة المُقيَّدة تذهب إلى شاشة الفحص لا إلى نموذج كلمة المرور، لأن الهبوط على الدخول بعد أن كان الجهاز قد قبل البيانات بالفعل سيجعل الاختيار كله غير مرئي. والقفزة نفسها تبني الصفحة باستدعاء AppRouter.resolve(RouteSettings(name: route)) مباشرة داخل PageRouteBuilder بتلاشٍ 450 ملّي ثانية — فالموجِّه دالة، وتستطيع البداية إعادة استخدامه دون المرور بـ onGenerateRoute.

A second address layer for automationطبقة عنوان ثانية لأغراض الآلية

A Dart ValueKey is invisible to the platform: UiAutomator2 and Appium cannot see it, so an automation suite is left addressing "the EditText above the Password field" or raw coordinates — both of which break the moment the design changes. SemanticId exists to fix exactly that. It wraps a subtree in Semantics(identifier: id, container: true), and Flutter publishes that identifier to Android as the node's resource-id — the very thing an Appium XPath can address. Ten widget files use it, giving stable handles such as login_button, go_to_sign_up_button, open_cart_button, hot_offers_list, open_map_button, save_favourite_button, reorder_button, biometric_login_button, use_password_button, plus the two parameterised families add_to_cart_button_<mealId> and cart_line_quantity_<mealId>.

Two design points are worth more than the API itself. Callers normally pass key: ValueKey(id) as well, so find.byKey in a widget test and resource-id on a device address the same widget with the same string — the two layers of the test suite cannot drift apart. And explicitChildNodes defaults to true because of a real bug: Flutter merges a subtree's labels into one accessibility node, which used to make a meal card surface as a single blob of text and its Add-to-Cart button vanish from the tree entirely, taking its resource-id with it. Declaring children explicit is what let the Appium suite reach a button nested inside a card. The optional label adds a human name beside the identifier so a screen reader still announces something useful, and — unlike an id — a label is localised.

قيمة ValueKey غير مرئية للنظام: فلا يرى UiAutomator2 ولا Appium شيئًا منها، ولا يبقى أمام مجموعة الاختبار الآلي سوى التعليب بـ «حقل EditText فوق كلمة المرور» أو بإحداثيات خام — وكلاهما ينكسر لحظة تغيّر التصميم. وSemanticId وُجدت لعلاج هذا بالتحديد. فهي تلفّ شجرة فرعية بـ Semantics(identifier: id, container: true)، وينشر Flutter هذا المعرّف إلى Android على أنه resource-id العقدة — وهو تحديدًا ما يستطيع XPath في Appium أن يُعنونه. وتستخدمها عشر ملفات ودجات، فتعطي عناوين ثابتة مثل login_button وgo_to_sign_up_button وopen_cart_button وhot_offers_list وopen_map_button وsave_favourite_button و reorder_button وbiometric_login_button وuse_password_button، إضافة إلى أسرتين مُوسَّطتين add_to_cart_button_<mealId> وcart_line_quantity_<mealId>.

ونقطتان في التصميم أهمّ من الواجهة نفسها. فالمستدعي يمرّر عادةً key: ValueKey(id) أيضًا، فيُعنون find.byKey في اختبار ودجة وresource-id على الجهاز الودجة نفسها بالسلسلة نفسها — فلا تتباعد طبقتا مجموعة الاختبار. وexplicitChildNodes قيمتها الافتراضية true بسبب خطأ حقيقي: يدمج Flutter تسميات الشجرة الفرعية في عقدة إمكانية وصول واحدة، وكانت بطاقة الطبق تظهر لذلك ككتلة نص واحدة ويختفي زر «أضف إلى السلة» من الشجرة بالكامل، آخذًا resource-id معه. والتصريح بالأبناء هو ما مكّن مجموعة Appium من الوصول إلى زر متداخّل داخل بطاقة. والتسمية الاختيارية label تضيف اسمًا بشريًا بجانب المعرّف حتى تُذيع تقنية المساعدة اسمًا مفيدًا — وبخلاف المعرّف، التسمية مترجمة.

Honest gap — onGenerateRoute could parse a deep link, and the router's default branch is commented "Unknown route (bad deep link): land on the splash rather than crash". But nothing in lib/ registers a link handler or reads Uri parameters. The manifest does carry one VIEW intent filter with the custom scheme streetbite — commented as streetbite://qa/reset for the Appium suite — but no Dart, Kotlin or Java code parses it. So a shared link cannot open a specific meal; the OS starts the app and the splash decides the destination, and the only real effect of an external link is activity recreation. Ship-quality deep linking would need a link-handler package plus a route-level argument schema (see §11). فجوة صريحة — كان يمكن onGenerateRoute أن يحلّ رابطًا خارجيًا، وحالة default معلَّق عليها "مسار غير معروف (رابط خارجي خاطئ): اهبط على البداية بدل الانهيار". لكن لا شيء في lib/ يسجّل معالج روابط، ولا يقرأ وسائط Uri. ويحمل الملف AndroidManifest.xml مرشّح قصد من نوع VIEW واحدًا بمخطط مخصّص هو streetbite — وتعليق المصدر يسمّيه streetbite://qa/reset لحزمة Appium — لكن لا كود يحلّله في Dart أو Kotlin أو جافا. فلا يستطيع رابط مشارك فتح طبق معيّن؛ يبدأ النظام التطبيق وتقرّر البداية الوجهة، والأثر الحقيقي الوحيد للرابط الخارجي هو إعادة إنشاء النشاط. وكان الربط العميق بجودة الإطلاق يحتاج حزمة معالج روابط، إضافة إلى مخطط وسائط على مستوى المسار (انظر §11).
