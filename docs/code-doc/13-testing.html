StreetBite code documentation · §13 Testing & QA

StreetBite code documentation · Part I · Section 13 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 13 من 18 · الفهرس الكامل

13 · Testing & QA13 · الاختبار وضبط الجودة

StreetBite is verified at three depths, and the interesting part is not the totals — it is that the layers found different bugs. Layer 1 is 99 automated tests inside the Dart VM (17 files, no device, ~40 s). Layer 2 is 6 Appium cases driving the installed release APK on a real handset. Layer 3 is a 51-case manual workbook, of which only 17 have been executed and passed.

The stated reason for layers 2 and 3 is in the QA pack itself: all fourteen defects raised were invisible to flutter analyze and flutter test, which stayed green throughout. A dependency resolved before registration, a login form that pre-filled a password, and an accessibility node that swallowed a button are all things a unit test cannot see, because none of them happen inside the Dart VM.

يُتحقّق من StreetBite على ثلاث أعماق، والمثير ليس المجاميع — بل أن الطبقات اكتشفت أخطاء مختلفة. الطبقة الأولى 99 اختبارًا آليًا داخل آلة Dart (17 ملفًا، بلا جهاز، نحو 40 ثانية). والطبقة الثانية 6 حالات Appium تُدير نسخة APK المثبّتة على جهاز حقيقي. والطبقة الثالثة workbook يدوي من 51 حالة، لم يُنفَّذ منه إلا 17 حالة ونجحت.

والسبب المعلن للطبقتين الثانية والثالثة موجود في حزمة الجودة نفسها: الأخطاء الأربعة عشر التي رُفعت كانت غير مرئية لـ flutter analyze وflutter test، وهما أخضران طوال الوقت. فثابت يُحلّ قبل تسجيله، ونموذج دخول يملأ كلمة المرور سلفًا، وعقدة إمكانية وصول تبتلع زرًا — ثلاثة أشياء لا يراها اختبار الوحدة، لأن لا شيء منها يحدث داخل آلة Dart.

Four conventions make these tests survivable. (1) Every widget file opens with TestWidgetsFlutterBinding.ensureInitialized() and SharedPreferences.setMockInitialValues(<String, Object>{}) — without the mock store the platform channel never answers and the test hangs rather than fails. (2) Dependencies are mocktail mocks of the abstract repositories, never of implementations, so a widget test drives the same cubit production uses. (3) Because openBiometricGate reaches its service through GetIt, a test registers FakeBiometricService once in setUpAll, guarded by if (!GetIt.I.isRegistered<BiometricService>()) — that indirection is why the biometric flow is testable at all, since local_auth has no channel in the test runner. (4) Cubits created by the harness are closed with addTearDown, so a leaked bloc subscription cannot make the 17th file fail because of something the 3rd file started.

The harness is deliberately a copy of production wiring: MultiBlocProvider with the three global cubits the screen reads, AppTheme.light, the real localisation delegates, and a stub onGenerateRoute that renders route:/name. That stub is what lets a test assert on a successful login's navigation without a Navigator stack. One sentinel, _useCubitLocale, makes the MaterialApp read its locale from LocaleCubit instead of a fixed value — the exact mechanism that makes the runtime EN/AR toggle work, and the reason an RTL test can flip language without re-pumping the app.

أربعة اصطلاحات تجعل هذه الاختبارات معتمدة. (1) كل ملف ودجة يفتتح بـ TestWidgetsFlutterBinding.ensureInitialized() ثم SharedPreferences.setMockInitialValues(<String, Object>{}) — بلا المخزن المقلَّد لا تجيب قناة النظام أبدًا، فيتوقّف الاختبار معلّقًا بدل أن يفشل. (2) التبعية تكون بمحاكاة mocktail لواجهات المستودعات المجرّدة لا لتنفيذاتها، فاختبار الودجة يقود Cubit الإنتاج نفسه. (3) ولأن openBiometricGate تصل إلى خدمتها عبر GetIt، يسجّل الاختبار FakeBiometricService مرة واحدة في setUpAll محميًا بـ if (!GetIt.I.isRegistered<BiometricService>()) — وهذه الإحالة هي سبب قابلية اختبار مسار البصمة أصلًا، إذ لا قناة لـ local_auth في مشغّل الاختبار. (4) والدوال التي تُنشئها بيئة الاختبار تُغلق بـ addTearDown، فلا تستطيع اشتراكات bloc مسرّبة أن تُفشل الملف السابع عشر بسبب شيء بدأه الملف الثالث.

والبيئة نسخة مقصودة من توصيل الإنتاج: MultiBlocProvider بالدوال العالمية الثلاث التي تقرأها الشاشة، وAppTheme.light، ومنسّقات الترجمة الحقيقية، وonGenerateRoute بديلة تعرض route:/name. وهذا البديل هو ما يسمح للاختبار بالتحقق من تنقّل الدخول الناجح دون مكدّس Navigator. وعلم واحد، _useCubitLocale، يجعل MaterialApp يقرأ لغته من LocaleCubit لا من قيمة ثابتة — وهي الآلية نفسها التي تجعل تبديل الإنجليزية/العربية يعمل أثناء التشغيل، وسبب قدرة اختبار RTL على قلب اللغة دون إعادة ضخّ التطبيق.

The bloc layer uses bloc_test, not manual pumping. cart_bloc_test.dart is seven blocTest<CartBloc, CartState> blocks, each declaring the initial state, the act that adds an event, and the expect list of states that must be emitted in order. That shape is what makes the money rules from §8 executable: add the same meal twice and the state must show quantity: 2 with one line, not two lines.

The domain tests pin a boundary, not a behaviour. order_lifecycle_test.dart builds an order N ago through a local helper and asserts against AppConstants.orderActiveWindow rather than a literal 45 — so changing the constant moves the tests instead of silently breaking them. One case sits exactly on the boundary and expects OrderStatus.past, which is what documents whether the window is inclusive; another asserts that a vendor-closed order is never resurrected by a fresh clock reading.

طبقة bloc تستخدم bloc_test لا الضخّ اليدوي. ملف cart_bloc_test.dart سبع كتل blocTest<CartBloc, CartState>، كل واحدة تُعلن الحالة الأولى، ثم act الذي يُضيف حدثًا، ثم قائمة expect بالحالات التي يجب أن تُصدَّر بالترتيب. وهذا الشكل هو ما يجعل قواعد المال في §8 قابلة للتنفيذ: أضف الطبق نفسه مرّتين فتُظهر الحالة quantity: 2 بسط واحد، لا سطّين.

اختبارات المجال تُثبّت حدًّا لا سلوكًا. يبني order_lifecycle_test.dart طلبًا منذ N عبر دالة مساعدة محلية، ويُسند إلى AppConstants.orderActiveWindow لا إلى 45 حرفية — فلو غيّر الثابت تحرّكت الاختبارات بدل أن تنكسر بصمت. وحالة واحدة على الحد تمامًا وتتوقّع OrderStatus.past، وهذا ما يوثّق ما إذا كانت النافذة شاملة؛ وحالة أخرى تجزم أن الطلب الذي أغلقه البائع لا يُبعث بقراءة ساعة جديدة.

The suite is a small Page-Object model: BaseTest (399 lines) holds all the lifecycle, Config (199) all the values, Waits (53) the explicit-wait helpers, SuiteListener (117) the reporting, LoginPage (236) and HomePage (249) the locators, and the three test classes contribute nothing but steps and assertions. testng.xml declares one <class> per feature, mirroring the manual suites one-to-one so a failing run maps straight onto a ticket.

Addressing is done the way §12 describes. Page objects find nodes with //*[starts-with(@resource-id, 'login_button')] — the identifier published by Semantics(identifier:) — and fall back to @text or @content-desc only for things the app does not tag, such as the "added to your cart" SnackBar. Locator strategy, not locator value, is the reason this suite survived redesign work: the ids are stable strings, whereas "the EditText above the Password field" is not.

المجموعة نموذج صفحات صغير: BaseTest (399 سطرًا) يحمل كل دورة الحياة، وConfig (199) كل القيم، وWaits (53) مساعدات الانتظار الصريح، وSuiteListener (117) التقارير، وLoginPage (236) وHomePage (249) مواضع العناصر، أما أصناف الاختبار الثلاثة فلا تساهم إلا بالخطوات والتأكيدات. ويعلن testng.xml <class> واحدًا لكل ميزة، محاكيًا المجموعات اليدوية واحدًا لواحد، حتى تُنسب جولة فاشلة مباشرة إلى تذكرة.

والوصول إلى العناصر يتم كما يصفه §12. تبحث كائنات الصف بعبارة XPath هي //*[starts-with(@resource-id, 'login_button')] — أي المعرّف الذي ينشره Semantics(identifier:) — وترجع إلى @text أو @content-desc فقط لما لا يوسمه التطبيق، مثل شريط «أُضيف إلى سلتك». استراتيجية التحديد لا قيمته هي سبب نجاة هذه المجموعة من أعمال إعادة التصميم: فالمعرّفات سلاسل ثابتة، بخلاف «حقل EditText فوق كلمة المرور».

Two lifecycle decisions carry the suite. The driver is created in @BeforeClass and quit in @AfterClass — one Appium session per class, because creating a session costs an APK re-launch and would dominate the runtime. But @BeforeMethod then wipes the app sandbox, because StreetBite persists its Firebase session and a plain restart would leave every test after the first one already signed in. The wipe prefers mobile: clearApp, falls back to pm clear through mobile: shell, and if both fail prints a loud warning rather than letting a "Login expected" test fail as a mysterious timeout. The comment records why the obvious choice is wrong: Appium 3 gates arbitrary shell access behind an "insecure" feature, so the shell route fails by default and silently degrades to a mere process restart — which is exactly the useless outcome.

Evidence is automatic: @AfterMethod writes a PNG named Class_method when the result is a failure, and the same is done inside fixtures through setupStep(...), because TestNG does not run @AfterMethod when @BeforeMethod throws — a broken fixture is precisely when seeing the screen matters most. SuiteListener appends every outcome to one flat target/suite-report.txt and truncates it on start: an append-only report lets forty old red lines sit under a green run, at which point the file is evidence of nothing.

قراران في دورة الحياة يحملان المجموعة. يُنشأ المُشغِّل في @BeforeClass ويُغلق في @AfterClass — جلسة Appium واحدة لكل صنف، لأن إنشاء الجلسة يعيد إطلاق APK وكان سيسيطر على زمن التنفيذ. لكن @BeforeMethod يمسح صندوق التطبيق بعدها في كل حالة، لأن StreetBite يحتفظ بجلسة Firebase، ولو اكتُفي بإعادة التشغيل لكان كل اختبار بعد الأول مسجَّل الدخول أصلًا. والمسح يفضّل mobile: clearApp، وإلا يرجع إلى pm clear عبر mobile: shell، وإذا فشل الاثنان يطبع تحذيرًا صريحًا بدل أن يفشل اختبار «نتوقّع الدخول» كخطأ مهلة غامض. ويوثّق التعليق خطأ الخيار البديهي: Appium 3 يحجب الوصول الحرّ إلى الصدفة خلف ميزة "insecure"، فمسار الصدفة يفشل افتراضيًا ويتدهور بصمت إلى إعادة تشغيل العملية فقط — وهو النتيجة عديمة الفائدة نفسها.

والدليل آلي: يكتب @AfterMethod صورة PNG باسم Class_method متى كانت النتيجة فشلًا، ويُفعل المثل داخل الأدوات التحضيرية عبر setupStep(...)، لأن TestNG لا يشغّل @AfterMethod حين يستثني @BeforeMethod — والإداة المعطوبة هي تحديدًا الوقت الذي يهمّ فيه رؤية الشاشة. وSuiteListener يُلحق كل نتيجة بملف مسطّح واحد هو target/suite-report.txt، ويبتدئه بـ قصّ: فالملف الذي يُلحق فقط يسمح لأربعين سطراً أحمر قديمًا بالبقاء تحت جولة خضراء، وحينها لا يعود دليلًا على شيء.

Configuration has a documented precedence chain. Config.java resolves each key in order — a Maven -D system property, then an environment variable (upper-cased, dots turned into underscores), then automation.properties. That is why the same suite runs on an emulator by default and on a physical handset with nothing but -Dappium.device=<serial>. Implicit waits are set to 0 deliberately, with the comment saying why: with Appium they hide real timing bugs and interact badly with element caching, so all waiting is explicit (15 s). The APK path, the package name (com.example.streetbite_capstone) and the seeded QA credentials all live in that one properties file rather than in Java — the only credential in the repository is the intentional demo account, which is a teaching-artefact decision, not a leak (see §14).

والإعدادات لها سلسلة أولوية موثّقة. يحلّ Config.java كل مفتاح بالترتيب: خاصية نظام بـ -D في Maven، فمتغيّر بيئة (أحرف كبيرة والنقاط شرط سفلية)، فـ automation.properties. ولهذا تعمل المجموعة نفسها على محاكي افتراضيًا وعلى هاتف حقيقي بشيء واحد فقط هو -Dappium.device=<serial>. الانتظارات الضمنية صفر عن قصد، والسبب مكتوب: مع Appium تُخفي أخطاء التوقيت الحقيقية وتتعامل بسوء مع تخزين العناصر، فكل انتظار صريح (15 ثانية). ومسار APK واسم الحزمة (com.example.streetbite_capstone) وبيانات حساب الجودة المزروعة كلها في ملف الخصائص ذاك لا في جافا — والمعرّف الوحيد في المستودع هو حساب تجريبي مُعلَن، وهو قرار تعليمي لا تسريب (انظر §14).

Layer 3 — the manual pack, and the honesty ruleالطبقة الثالثة — الحزمة اليدوية وقاعدة الصراحة

manual_qa/ ships a workbook (TestPlan_and_TestCases.xlsx) holding the plan, the suites, the execution record, the traceability matrix and a Defect Log that mirrors the Jira board one-to-one; a one-page closure summary (TestClosureSummary.pdf); six screenshots; and four Python generators. Its opening line is a status, not a boast: "Status: NOT READY TO CLOSE. 17 of 51 cases have been executed and passed; 34 are still recorded as Blocked."

The rule that produces those numbers is worth quoting: "Nothing is marked 'passed' on the strength of having written it. A case is marked executed only if the release APK was installed on a real device and the behaviour was observed." The 34 remaining cases are therefore Blocked, not silently green — the pack states that an honest 17/51 is worth more than a fabricated 51/51. Screenshots are numbered to match case IDs (04_home_feed.png, 05_home_arabic.png, 06_cart_empty.png, 10_dark_mode.png) so evidence and case line up without guesswork.

The pack is generated, not hand-edited: build_qa_workbook.py writes the base plan, apply_execution_results.py layers the real 17/51 record, apply_defect_log.py adds the observed defects, and build_closure_summary.py renders the PDF — in that order, because each script edits the workbook the previous one produced. Skipping step 2 leaves the deliverable showing the plan rather than what was observed, which is the failure mode the ordering comment exists to prevent.

تصدّر manual_qa/ workbook (هو TestPlan_and_TestCases.xlsx) يحمل الخطة والمجموعات وسجلّ التنفيذ ومصفوفة التتبّع وسجلّ أخطاء يطابق لوحة Jira واحدًا لواحد؛ وملخّص إغلاق من صفحة واحدة (TestClosureSummary.pdf)؛ وست لقطات؛ وأربع دوال توليد بلغة Python. وسطره الافتتاحي حالة لا فخر: «الحالة: غير جاهز للإغلاق. نُفِّذت 17 من 51 حالة ونجحت؛ و34 ما زالت مسجّلة كمحجوبة.»

والقاعدة التي تُنتج هذه الأرقام تستحق الاقتباس: «لا شيء يُوسم بـ«نجح» لمجرد أننا كتبناه. والحالة تُوسم بـ«منفَّذة» فقط إن ثُبِّت APK الإطلاق على جهاز حقيقي ولُوحظ السلوك». والـ 34 الباقية لذا محجوبة، لا خضراء بصمت — وتقول الحزمة إن 17/51 صادقة خير من 51/51 مختلَقة. واللقطات مرقّمة مطابقةً لمعرّفات الحالات (04_home_feed.png، 05_home_arabic.png، 06_cart_empty.png، 10_dark_mode.png) حتى تُطابق اللقطة حالتها دون تخمين.

والحزمة مولَّدة لا محرَّرة يدويًا: build_qa_workbook.py يكتب الخطة الأساس، ثم apply_execution_results.py يُركّب سجل 17/51 الحقيقي، ثم apply_defect_log.py يضيف الأخطاء المرصودة، ثم build_closure_summary.py يولّد الـ PDF — بهذا الترتيب، لأن كل دالة تحرّر ما أنتجتها سابقتها. وتخطّي الخطوة الثانية يترك المُسلَّم يعرض الخطة لا ما رُصد، وهذا هو النمط الذي وُجد تعليق الترتيب لمنعه.

Read as a distribution, the log is a lesson about layers: 7 of 14 are wiring or backend problems (SB-106, 107, 108, 114, 115, 116, 118) that only a cold start against real services can surface; 4 were found by the Appium suite, and two of those are the suite testing itself — SB-112 and SB-113 are automation defects, not app defects. SB-111 is the one that would have shipped: a login form with a pre-filled password is a security smell that no widget test complained about, because in the test the field was empty.

SB-119 is classified honestly as a credential problem, not a code problem — the SDK reports StatusCode=INVALID_ARGUMENT then Authorization failure, and tiles will not draw until a valid key is supplied in android/key.properties (which is gitignored and therefore absent from the repository) or Maps SDK for Android is enabled in Google Cloud Console.

لو قُرئ السجلّ كتوزيع فلغةٌ عن الطبقات: 7 من 14 مشاكل توصيل أو خلفية (SB-106، 107، 108، 114، 115، 116، 118) لا يكشفها إلا بدء بارد مقابل خدمات حقيقية؛ و4 وجدتها مجموعة Appium، واثنان منها تختبر المجموعة نفسها — فـ SB-112 وSB-113 عيبا آلية لا عيبا تطبيق. وSB-111 هو الذي كان سيُصدَّر: نموذج دخول بكلمة مرور محشوّة لم يشتكِ منه أي اختبار ودجة، لأن الحقل فيه كان فارغًا.

وSB-119 مُصنَّف بصراحة كمشكلة معرّف لا كود — يبلّغ SDK عن StatusCode=INVALID_ARGUMENT ثم Authorization failure، ولن تُرسم البلاطات حتى يوضع مفتاح صالح في android/key.properties (وهو مستثنى من git وغائب لذا عن المستودع) أو حتى يُفعَّل Maps SDK for Android في Google Cloud Console.

What is deliberately not coveredما ليس مُغطًّى عن قصد

Be exact about the limits. There is no CI: no .github/ directory, no pipeline — the three commands above are run by hand, which means "green" is a statement about the last manual run, not a standing guarantee. There are no golden/screenshot widget tests, so the four appearance variants are compared by eye. There is no coverage gate; flutter test --coverage is runnable but nothing reads the output. No test touches real Firebase or real Google Maps, so SB-114 and SB-119 were necessarily device findings. And the Appium suite is 6 cases against a screens-and-tabs app — the biometric gate, the offline cache fallback and the Arabic receipts have no device-level regression behind them. Stating the 34 blocked manual cases is part of the deliverable for the same reason. كن دقيقًا في الحدود. لا CI: لا مجلد .github/ ولا مسار أنابيب — الأوامر الثلاثة أعلاه تُشغَّل يدويًا، فـ «أخضر» خبر عن آخر تشغيل يدوي لا ضمان دائم. ولا اختبارات ذهبية لودجات، فتُقارن المظاهر الأربعة بالعين. ولا حدّ لتغطية؛ flutter test --coverage قابل للتشغيل لكن لا أحد يقرأ مخرجه. ولا اختبار يلمس Firebase الحقيقي أو خرائط Google الحقيقية، ولذا كان SB-114 وSB-119 بالضرورة نتائج جهاز. ومجموعة Appium ست حالات مقابل تطبيق شاشات وتبويبات — فبوابة البصمة، والتحوّل إلى المخزن حين ينقطع الاتصال، والإيصالات العربية، ثلاثة بلا انحدار على مستوى الجهاز. وذكر الحالات الـ 34 المحجوبة جزء من المُسلَّم لهذا السبب نفسه.
