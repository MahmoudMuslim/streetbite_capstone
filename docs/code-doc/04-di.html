StreetBite code documentation · §04 Composition root & dependency injection

StreetBite code documentation · Part I · Section 04 of 18 · Full indexتوثيق كود StreetBite · الجزء الأول · القسم 04 من 18 · الفهرس الكامل

04 · Composition root & dependency injection04 · جذر التركيب وحقن التبعيات

lib/injection.dart (390 lines) is the only file in the app that names a concrete implementation. It exposes final GetIt sl = GetIt.instance and one function, configureDependencies(), called once from main() before runApp. It performs 45 registrations: 24 lazy singletons, 1 eager singleton, and 20 factories.

Everything is registered inside one sequence that tolerates failure, and the order is load-bearing — see the first step below.

ملف lib/injection.dart (390 سطرًا) هو الملف الوحيد في التطبيق الذي يسمي تنفيذًا ملموسًا. يكشف عن final GetIt sl = GetIt.instance ودالة واحدة هي configureDependencies()، وتُستدعى مرة واحدة من main() قبل runApp. ينفذ الملف 45 تسجيلًا: 24 مفردة كسولة، ومفردة فورية واحدة، و20 مصنعًا.

كل شيء مسجل داخل تسلسل واحد يتحمل الأخطاء، وترتيبه مهم جدًا — راجع أول خطوة أدناه.

Why FirestoreService is registered first · لماذا تُسجَّل FirestoreService أولًا

_initFirebaseSafely() resolves sl<FirestoreService>() in order to hand it the Firebase instance. Resolving a type that has not been registered throws out of GetIt and would abort the rest of configureDependencies(), leaving every Cubit unregistered — which then crashes main() on an empty screen. Registering it first turns a fatal ordering mistake into an impossible one.

تستدعي _initFirebaseSafely()النوع sl<FirestoreService>() لكي تمنحه نسخة Firebase. واستدعاء نوع لم يُسجل بعد يرمي استثناءً من GetIt ويُجهض بقية configureDependencies()، فتبقى كل الـ Cubits غير مسجلة، ثم ينهار main() على شاشة فارغة. تسجيلها أولًا يحوّل خطأ الترتيب القاتل إلى خطأ مستحيل الحدوث.

Boot order in main()ترتيب الإقلاع في main()

  1. WidgetsFlutterBinding.ensureInitialized() — mandatory before any plugin call.
  2. SystemChrome.setPreferredOrientations — the app is portrait-only, both directions.
  3. configureDependencies() then _prepareAppState() (loads the persisted appearance and language), inside one try that only debugPrints.
  4. LiquidGlassWidgets.initialize() in its own try: a device with no usable GPU loses the glass look but keeps the app.
  5. _isGraphWired() checks the seven state objects are registered. If not, _StartupFailureApp is rendered — a dependency-free screen that prints flutter clean && flutter pub get instead of crashing inside runApp, the one place with no safety net.
  6. runApp(LiquidGlassWidgets.wrap(... StreetBiteApp(...))) with all seven Cubits resolved from sl and passed as constructor arguments.
  1. WidgetsFlutterBinding.ensureInitialized() — إلزامي قبل أي نداء لإضافة.
  2. SystemChrome.setPreferredOrientations — التطبيق عمودي الاتجاه فقط وباتجاهيه.
  3. configureDependencies() ثم _prepareAppState() (الذي يحمّل المظهر واللغة المحفوظَين) داخل try واحد يكتفي بـ debugPrint.
  4. LiquidGlassWidgets.initialize() في try مستقل: جهاز بلا معالج رسومات صالح يفقد الشكل الزجاجي لكنه يحتفظ بالتطبيق.
  5. _isGraphWired() تتحقق من تسجيل الكائنات السبعة. وإن لم تُسجَّل يُعرض _StartupFailureApp — شاشة بلا تبعيات تطبع flutter clean && flutter pub get بدلًا من الانهيار داخل runApp، وهو الموضع الوحيد بلا شبكة أمان.
  6. runApp(LiquidGlassWidgets.wrap(... StreetBiteApp(...))) بعد استدعاء الـ Cubits السبعة من sl وتمريرها كوسائط بناء.

Firebase bootstrap: a failure that must not be fatalتهيئة Firebase: فشل يجب ألا يكون قاتلًا

_initFirebaseSafely() calls Firebase.initializeApp(), then configure(FirebaseFirestore.instance). Any throw — missing google-services.json, no Play Services, a network error — lands in the catch, which calls configure(null) inside its own try so that even the fallback cannot abort the rest of the graph. With _firestore == null the singleton reports isAvailable == false and every repository transparently uses its local data source.

Then _waitForAuthSessionRestore() awaits the first value of FirebaseAuth.instance.userChanges() with a 10-second timeout. initializeApp() returning does not mean Auth is ready: the SDK reloads a saved session from disk asynchronously, so currentUser is briefly null. Reading it inside that window made the app conclude nobody was signed in, start Firestore requests with no token, and receive PERMISSION_DENIED: Missing or insufficient permissions — byte-for-byte identical to the message a wrong security rule produces. A fresh sign-in always worked, because login populates Auth synchronously; only cold restarts failed.

تستدعي _initFirebaseSafely() الدالة Firebase.initializeApp() ثم configure(FirebaseFirestore.instance). أي رمي — غياب google-services.json، أو عدم وجود خدمة Google Play، أو خطأ شبكة — يستقر في catch التي تستدعي configure(null) داخل try خاص بها حتى لا يُجهض البديل نفسه بقية رسم الشجرة. وعندئذ تكون _firestore == null فتُبلِغ المفردة بـ isAvailable == false وتستخدم كل مستودع مصدره المحلي بشفافية.

ثم تنتظر _waitForAuthSessionRestore() أول قيمة من FirebaseAuth.instance.userChanges() بمهلة 10 ثوانٍ. رجوع initializeApp() لا يعني أن المصادقة جاهزة: تُعيد الأداة تحميل الجلسة المحفوظة من القرص بشكل غير متزامن، فيبقى currentUser معادلًا لـ null لحظة قصيرة. والقراءة داخل تلك النافذة تجعل التطبيق يظن أن أحدًا لم يسجل الدخول، فيبدأ طلبات Firestore بلا رمز وصول ويستقبل PERMISSION_DENIED: Missing or insufficient permissions — وهو نص مطابق تمامًا لما تنتجه قاعدة حماية خاطئة. تسجيل الدخول الجديد كان يعمل دائمًا لأن الدخول يملأ المصادقة بشكل متزامن؛ والفشل كان يحدث في الإقلاع البارد فقط.

Seeding the QA accountتهيئة حساب الاختبار

_seedQaAccount() deliberately lives in the composition root: main.dart must never resolve a concrete data-layer class. The account is created in both stores — the on-device store the offline fallback reads, and Firebase Auth that login() talks to first. Seeding only the local store produces a confusing bug where sign-in is rejected even though the account "exists".

It is idempotent and non-fatal, and it contains a hard-won detail: createUserWithEmailAndPassword signs the new user in as a side effect, so a sign-out is required — but only when this call actually authenticated someone. An unconditional sign-out ran on every launch and logged the real user out of their own session: the splash restored it, and the composition root destroyed it again.

تسكن _seedQaAccount() في جذر التركيب عن قصد: يجب ألا تستدعي main.dart صنفًا ملموسًا في طبقة البيانات. يُنشأ الحساب في كلا المخزنين — المخزن المحلي الذي يقرأه المسار غير المتصل، وFirebase Auth الذي تتحدث إليه login() أولًا. وتهيئة المخزن المحلي وحده تُنتج خطأً محيرًا يُرفض فيه تسجيل الدخول رغم أن الحساب «موجود».

الدالة قابلة للتكرار وغير قاتلة، وفيها تفصيل ثمنه باهظ: createUserWithEmailAndPassword يسجل دخول المستخدم الجديد كتأثير جانبي، لذا يلزم تسجيل خروج — لكن فقط إذا كان هذا النداء هو من سجّل الدخول فعلًا. كان تسجيل الخروج غير المشروط يجري في كل إقلاع ويُخرج المستخدم الحالي من جلسته: تستعيدها شاشة البداية، فيهدمها جذر التركيب من جديد.

Testability payoff · العائد في الاختبار

Because Cubits receive abstract use cases, a widget test never touches Firebase: it constructs AuthCubit with mocktail doubles and pumps the screen. That is what the 15 test files do; none of them needs a running backend.

لأن الـ Cubits تستقبل حالات استخدام مجرّدة، لا تلمس اختبارات الـ Widget خدمة Firebase أبدًا: تبني AuthCubit ببدائل mocktail وتعرض الشاشة. هذا ما تفعله ملفات الاختبار الخمسة عشر؛ ولا يحتاج أي منها إلى خادم يعمل.
